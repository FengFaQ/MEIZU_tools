## 0. 先理解一个前提：三种"身份文件"

魅族高通的设备，BL 锁状态由**分区内容**决定，不由某个开关决定。
所以"解锁"本质是"往特定分区写特定字节"。这需要两把钥匙：

| 名称 | 存哪 | 长度 | 作用 | 缺失后果 |
|---|---|---|---|---|
| **解锁码** `blunlockcode` | `res\<product>\bak\blunlockcode.txt` | 512 字符（256 字节） | 解锁时写入 private 分区，或切成 16 段喂给 `fastboot oem unlock:` | 无法解锁 |
| **授权码** `edlauthcode` | `res\<product>\bak\edlauthcode.txt` | 512 字符（256 字节） | 9008 下 Firehose 握手的签名，证明"这是授权工具" | 无法 9008 读写 |
| **解锁 mzkv** `mzkv_unlock.img` | `res\<product>\bak\mzkv_unlock.img` | 分区镜像 | 新机型的解锁载体（替代 private 方案） | 无法解锁 mzkv 机型 |

> 关键认知：**授权码不是解锁码**。授权码是给 fh_loader 用的（`qcedlcmdhelper.exe -m sig`），
> 解锁码是写进分区的数据。二者来源、用途、校验方式完全不同。

哪个机型要什么，由 `dev.csv` 的 `blplan` 字段决定：

| blplan | 需要解锁码 | 需要授权码 | 需要解锁 mzkv |
|---|---|---|---|
| `auth-private` | ✅ 必须 | 推荐（缺失则降级走 Fastboot 解锁） | ❌ |
| `auth-mzkv-sig` | ❌ | ✅ 必须 | ✅ 必须 |
| `auth-mzkv-nosig` | ❌ | ❌ | ✅ 必须 |
| `odm-1` / `odm-2` / `odm-note8` | ❌ | ❌ | ❌ |

### 1.2 PRIVATE 方案（`L289`–`L375`）

三步：读设备 ID → 换取码 → 导入码。

#### 步骤 1：读取设备 ID（三条通路，任选）

菜单项 `1` 走默认通路，`11` 强制 Fastboot，`111` 强制 9008（`L298-L302`）：

| 通路 | 触发条件 | 实现 | 取到的字段 |
|---|---|---|---|
| **ADB**（默认） | 开机 + USB 调试 | `call mzbox adbchkfinddev` + `call mzbox adbreadinfo`（L310-311） | `chipid`、`socid` |
| **Fastboot** | `product==meizu20inf` 自动走此路，或手选 `11` | `call chkdev fastboot` + `call mzbox fbreadinfo`（L315-317） | `chipid`、`socid` |
| **9008** | 手选 `111` | `call chkdev qcedl` + `call mzbox edlreadinfo <端口> <引导路径>`（L320-322） | `chipid`、`socid` |

> **设计要点**：`meizu20inf`（20 无界版）不支持 9008，所以 `L299` 硬编码让它的 `1` 走 Fastboot。

读到的 ID 落盘为纯文本（`L330`）：

```
[ChipID]<chipid>
[SocID]<socid>
```

> 注意 `L330` 用的是 `>` 写第一行、`>>` 追加后两行，**不是 CRLF 问题**，
> 而是 `echo.>>file` 单独补一个换行 —— 这是 CMD 里制造空行的惯用法。

失败判定（`L327-L328`）：chipid 或 socid 任一为空即 `goto SAVEDATA-PRIVATE-READID-FAILED`。

#### 步骤 2：换取码（`L338`）

纯人工流程：`call open common https://kdocs.cn/l/cu2VFGm6ZhxS`
打开在线文档，把上一步的 `devid_<时间戳>.txt` 内容提交给作者，人工返回两个 512 字符的码。

> 这是**整个工具箱唯一的"服务端"**，而且是人工的。新工程若要自动化，这里是最大改造点。

#### 步骤 3：导入码（`L343`–`L375`）

用一个**模板文件 + 记事本**做输入界面（`L344-L353`）：

```bat
:: 生成模板
echo.# [blunlockcode]A1B2C3D4E5F6... 在[blunlockcode]后填写解锁码 >%tmpdir%\code.txt
echo.# [sig]A1B2C3D4E5F6...          在[sig]后填写授权码 >>%tmpdir%\code.txt
echo.请按照示例, 在下方填写: >>%tmpdir%\code.txt
echo.[blunlockcode]>>%tmpdir%\code.txt
echo.[sig]>>%tmpdir%\code.txt
:: 阻塞等待用户编辑
start /wait tool\Win\Notepad3\Notepad3.exe %tmpdir%\code.txt
```

解析用 `for /f "tokens=2 delims=[] "`（`L357`、`L367`）——
以 `[` `]` 和空格为分隔符取第 2 段，即 `[blunlockcode]` 后面的内容：

```bat
for /f "tokens=2 delims=[] " %%a in ('type %tmpdir%\code.txt ^| find /v "# " ^| find "[blunlockcode]"') do set blunlockcode=%%a
```

`find /v "# "` 是**排除注释行**（模板里以 `# ` 开头的示例行）。

**长度校验**（`L358-L360`）—— 三重判断，非常严谨：

```bat
if "%blunlockcode%"==""             → 未填写
if "%blunlockcode:~511,1%"==""      → 不足 512 字符（第 512 个字符取不到）
if not "%blunlockcode:~512,1%"==""  → 超过 512 字符（第 513 个字符能取到）
```

> `%var:~511,1%` 是 CMD 的子串语法，取 0-based 第 511 位（即第 512 个字符）。
> 这是**不用正则就能精确校验定长**的经典手法，很值得在新工程里保留思路。

**落盘**（`L361-L362`）：主副本 + 带时间戳的历史副本双写：

```bat
echo.%blunlockcode% >res\%product%\bak\blunlockcode.txt
copy /Y res\%product%\bak\blunlockcode.txt res\%product%\bak\blunlockcode_%baktime%.txt
```

### 1.3 MZKV 方案（`L189`–`L287`）

新机型（魅族 22 起）改用 mzkv 分区承载解锁信息。流程变成六步：

| # | 步骤 | 实现 | 关键点 |
|---|---|---|---|
| 1 | 读取设备 ID | `mzbox adbchkfinddev` + `adbreadinfo` → `socid` | **只取 socid，不取 chipid** |
| 2 | 获取授权码 | 打开在线文档人工申请 | 仅 `auth-mzkv-sig` 需要（`L226` 对 nosig 直接跳过） |
| 3 | 导入授权码 | 同上模板法，只解析 `[sig]` | 512 字符校验 |
| 4 | 回读原机 mzkv | `read qcedl mzkv ...` → 打包成 7z | 见下 |
| 5 | 获取解锁 mzkv | 上传打包的 mzkv，人工返回解锁版 | 在线文档 |
| 6 | 导入解锁 mzkv | 选 img 或 7z，落地成 `mzkv_unlock.img` | 见下 |

**步骤 4 的打包细节**（`L259-L267`）—— 为什么必须打包：

```bat
md tmp\mzkv
copy /Y res\%product%\bak\mzkv_%baktime%.img tmp\mzkv\mzkv.img
cd tmp\mzkv
7z.exe a -mx9 -slp -ssp -t7z -y mzkv.7z
```

`-slp`（symlink 存为链接）`-ssp`（不存盘符前缀）是关键：保证解包后路径可复现。
产物 `mzkv.7z` 交给作者，作者返回解锁版。

**步骤 6 的三格式兼容**（`L277`–`L286`）—— 很有参考价值：

```bat
call sel file s %framework_workspace%\.. [img][7z]
set mzkvpath=%sel__file_path%& set mzkvtype=%sel__file_ext%

:: 先删旧文件，避免"新文件导入失败但旧文件还在"的假成功
if exist res\%product%\bak\mzkv_unlock.img del res\%product%\bak\mzkv_unlock.img

:: 按扩展名分三种处理
if "%mzkvtype%"=="img" copy /Y %mzkvpath% res\%product%\bak\mzkv_unlock.img
if "%mzkvtype%"=="bin" copy /Y %mzkvpath% res\%product%\bak\mzkv_unlock.img
if "%mzkvtype%"=="7z"  7z.exe e -aoa -o...\res\%product%\bak -slp -y -ir!mzkv_unlock.img %mzkvpath%

:: 存在性判定 + 历史副本
if exist res\%product%\bak\mzkv_unlock.img copy /Y ... mzkv_unlock_%baktime%.img && 已导入 || goto FATAL
if not exist res\%product%\bak\mzkv_unlock.img → 导入失败，提示可能选错文件
```

> **先删后写**是这里最值得学的细节：如果不先删，7z 解包失败时旧文件仍在，
> 后面的"存在即成功"判断会误判为导入成功。这类"脏状态"是批处理最容易埋的坑。

## 2. 解锁 BL 与上锁 BL

### 2.1 解锁 BL 总览

**入口**：主菜单 `1` → `:UNLOCKBL`（`L687`）

`L718` 是整个功能的分发点：

```bat
goto UNLOCKBL-%blplan%
```

于是 `blplan=odm-1` 跳到 `:UNLOCKBL-ODM-1`，`blplan=auth-private` 跳到 `:UNLOCKBL-AUTH-PRIVATE`。
**机型表的字段名直接就是标签名**，这是数据驱动的极致体现。

| blplan | 标签 | 难度 | 核心手法 |
|---|---|---|---|
| `auth-mzkv-sig` / `nosig` | `L720` 起 | 中 | 9008 刷入解锁 mzkv |
| `auth-private` | `L753` 起 | 高 | 9008 改 private.img 偏移 / Fastboot 分段下发 |
| `odm-1` | `L857` | 中 | 9008 改 frp 分区 + Fastboot 确认 |
| `odm-2` | `L880` | 低 | Fastboot oem unlock:<SN> |
| `odm-note8` | `L897` | 高 | 刷解锁 aboot，解锁后必须还原 |

### 2.2 MZKV 方案解锁（`L720`–`L752`）

三个标签依次排列（`L720-L722`），靠"落穿"实现共用：

```bat
:UNLOCKBL-AUTH-MZKV-SIG
:UNLOCKBL-AUTH-MZKV-NOSIG
:UNLOCKBL-AUTH-MZKV          ← 实际逻辑从这里开始
```

**前置检查**（`L723-L733`）：
- L725：`mzkv_unlock.img` 必须存在
- L727：`auth-mzkv-nosig` 直接跳过授权码检查
- L729-L733：`edlauthcode.txt` 必须存在且恰好 512 字符

**执行序列**（`L735`–`L751`）：

```
1. chkdev qcedl rechk 1              进 9008
2. write qcedlsendfh <端口> <devprg> auto    发 Firehose 引导 + 配置端口
3. read  qcedl mzkv bak\mzkv_<ts>.img notice    ★ 先备份原 mzkv
4. write qcedl mzkv bak\mzkv_unlock.img         ★ 刷入解锁 mzkv
5. reboot qcedl qcedl                          软重启回 9008
6. chkdev qcedl rechk 1
7. write qcedlsendfh ...                       再发引导
8. mzbox edlreadinfo → mzbox__edlreadinfo__unlocked   验证
9. write qcedl misc misc_wipedata.img          ★ 清数据标记
10. reboot qcedl system                        重启
```

**验证环节**（`L745-L747`）区分三态：

```bat
if "%mzbox__edlreadinfo__unlocked%"==""    → 检查失败（不阻断，仅警告）
if "%mzkv...unlocked%"=="no"                → 解锁失败（不阻断，仅警告）
if "%mzkv...unlocked%"=="yes"               → 解锁成功
```

> **重要设计取舍**：验证失败**只警告不中止**。理由是解锁已经写入设备，
> 中止也回不去；让用户继续走完"清数据 + 重启"流程反而更可能被救活。

**`misc_wipedata.img` 是什么**：一个 8KB 的 misc 分区镜像，
刷入后设备下次启动会进入 recovery 并自动执行 `wipe data`。
这是绕过"解锁后必须格式化"的手动步骤的自动化手段。

### 2.3 PRIVATE 方案解锁（`L753`–`L856`）★ 最复杂

这是全工程最精巧的一段，因为它有**两条完全不同的技术路线**，还要动态选择。

#### 路线选择（`L754`–`L777`）

```bat
set unlockbl__auth_private__forcefb=n
if "%product%"=="meizu20inf" set unlockbl__auth_private__forcefb=y    ← L757 硬编码特例

if not exist blunlockcode.txt            → 报错返回（解锁码必须）
校验 blunlockcode 恰好 512 字符
if "%unlockbl__auth_private__forcefb%"=="y"  → goto PRIVATE-FB          ← 强制走 Fastboot

if not exist edlauthcode.txt              → 警告，降级走 Fastboot      ← L769
校验 edlauthcode 恰好 512 字符             → 不合格则降级走 Fastboot    ← L772-773
→ goto PRIVATE-EDL                                                       ← 两条都合格才走 9008
```

> **设计精髓**：有授权码走 9008（更强、更彻底），没授权码自动降级走 Fastboot。
> 用户不需要懂两者的区别，脚本自动选最优可用路径。

#### 路线 A：Fastboot 分段下发（`L778`–`L809`）

**核心发现**：512 字符的解锁码被切成 **16 段 × 32 字符**，逐条执行：

```bat
fastboot.exe oem unlock:%blunlockcode:~0,32%      ← 第 1 段，偏移 0
fastboot.exe oem unlock:%blunlockcode:~32,32%     ← 第 2 段，偏移 32
fastboot.exe oem unlock:%blunlockcode:~64,32%     ← 第 3 段，偏移 64
...
fastboot.exe oem unlock:%blunlockcode:~480,32%    ← 第 16 段，偏移 480
```

`L785`–`L800` 整 16 行，格式完全一致，只有偏移量和提示文字不同。
而且提示文字是**藏头**的（`L785-L800` 的 ECHOC 内容拼起来）：

```
极致 源 于 梦想 / 追求 源 于 热爱 / 创造 无 界 可能 / 为 你 开 启 未来
```

> 这是作者的彩蛋，但也带来一个实现问题：**16 条命令硬编码**，
> 新工程应当改成循环 —— 见 §6 建议。

**每条命令的失败处理**：`||` 后接提示 + `pause` + 继续下一条，**不中止**。
理由同上：解锁码是一次性的，中途停下设备状态更糟。

**Fastboot 路线收尾**（`L805-L809`）：

```bat
if "%unlockbl__auth_private__forcefb%"=="y" (
    call write fastboot misc tool\Android\misc_wipedata.img
    call reboot fastboot system
    goto UNLOCKBL-DONE)
```

#### 路线 B：Fastboot 解锁后转 9008 改 private（`L810`–`L856`）

```bat
if "%edlplan%"=="cmd"      → call reboot fastboot qcedl          ← 命令直转
if "%edlplan%"=="key"      → 提示用户长按电源+音量
if "%edlplan%"=="edlcable" (                                      ← L813-817
    ECHOC 现在请换用9008线连接电脑
    call chkdev fastboot
    call reboot fastboot fastboot)     ← 先转 fastboot 再让线缆生效
```

**9008 阶段核心**（`L819`–`L856`）：

```
1. chkdev qcedl rechk 1
2. write qcedlsendfh <端口> <devprg> auto
3. read  qcedl private bak\private_<ts>.img notice    ★ 备份原 private
4. copy bak\private_<ts>.img → tmp\private.img
5. ── 用 HexTool 在 4 个固定偏移写入解锁标记 ──
6. write qcedl private tmp\private.img                ★ 刷回
7. reboot qcedl qcedl  →  chkdev  →  sendfh
8. mzbox edlreadinfo 验证 unlocked
9. write qcedl misc misc_wipedata.img
10. reboot qcedl system
```

**HexTool 的四次写入**（`L828`–`L834`）—— 这是全工程最核心的"厂商私有协议知识"：

```bat
::HexTool.exe <文件> <偏移(十进制)> <长度> <十六进制数据>

HexTool.exe tmp\private.img 00069632 4   4C4F434B                              ← 写 "LOCK"
HexTool.exe tmp\private.img 00069636 256 %blunlockcode%                        ← 写 256 字节解锁码
HexTool.exe tmp\private.img 00069892 16  666163746F7279000000000000000000      ← 写 "factory"
HexTool.exe tmp\private.img 00069908 16  %str%                                 ← 写版本标记
```

逐一解读：

| 偏移（十进制） | 偏移（十六进制） | 长度 | 内容 | ASCII | 含义 |
|---|---|---|---|---|---|
| 69632 | `0x11000` | 4 | `4C4F434B` | `LOCK` | 标记块头 |
| 69636 | `0x11004` | 256 | 解锁码 | — | 512 字符解锁码按十六进制展开 |
| 69892 | `0x11104` | 16 | `666163746F7279…` | `factory` | 模式名 |
| 69908 | `0x11114` | 16 | 见下 | 见下 | 版本标记 |

**版本标记 `str` 的两套值**（`L831`–`L834`）：

```bat
set str=6D54657374332E31302E372E30000000          ← 默认: "mTest3.10.7.0"
if "%product%"=="meizu18s"    set str=726465352E342E352E30000000000000   ← "rde5.4.5.0"
if "%product%"=="meizu18sPro" set str=726465352E342E352E30000000000000   ← 同上
```

| 十六进制 | ASCII | 用于 |
|---|---|---|
| `6D54657374332E31302E372E30` | `mTest3.10.7.0` | 绝大多数机型 |
| `726465352E342E352E30` | `rde5.4.5.0` | 18s / 18sPro |
| `6D65697A75626C2E636F6D` | `meizubl.com` | 注释里提到，未启用 |

**被注释掉的第二组偏移**（`L840-L843`）—— 极具参考价值：

```bat
::HexTool.exe tmp\private.img 00081920 4   4C4F434B   ← 0x14000
::HexTool.exe tmp\private.img 00081924 256 %blunlockcode%
::HexTool.exe tmp\private.img 00082180 16  666163746F7279...
::HexTool.exe tmp\private.img 00082196 16  6D54657374332E31302E372E30
```

即 `0x11000` 和 `0x14000` **两个位置都要写**，且内容完全相同。
作者注释说明 `0x14000` 是"fastboot 码，应该不用人为修改"—— 说明某些机型
只认 `0x14000`，某些只认 `0x11000`。

> ⚠️ **这是新工程必须搞清楚的地方**：到底该写哪个偏移、还是两个都写，
> 需要按机型区分。参考实现里这一段被注释掉了（等于只写 0x11000），
> 可能正是某些机型解锁失败的原因之一。**建议在新工程里做成机型可配置项。**

### 2.4 ODM-1 方案（`L857`–`L879`）：改 frp 分区

思路：把 frp（Factory Reset Protection）分区的**最后一个字节改成 01**，
让 Fastboot 认为"已经恢复出厂"，从而允许 `flashing unlock`。

```bat
1. chkdev qcedl rechk 1
2. write qcedlsendfh ...
3. read qcedl frp bak\frp_<ts>.img noprompt        ★ 备份
4. copy frp_<ts>.img → tmp\frp_unlock.img
5. busybox.exe stat -t tmp\frp_unlock.img          ← 取文件大小
6. call calc s var nodec %var% 1                   ← var = size - 1  ★ 算出最后一字节偏移
7. HexTool.exe tmp\frp_unlock.img %var% 1 01       ← 最后一字节写 0x01
8. write qcedl frp tmp\frp_unlock.img              ★ 刷回
9. chkdev fastboot rechk 1                         ← 转 Fastboot
10. info fastboot → 已解锁则跳过
11. fastboot.exe flashing unlock                   ← 触发官方解锁
12. call choice choice [1][2][3]                   ← ★ 此处有 BUG，见下
```

**第 6 步值得注意**：用 `calc s <变量> nodec <数1> <数1>` 做减法求偏移，
再用 `%var%` 传给 HexTool。这是"动态偏移"的通用做法 —— 不依赖固定分区大小。

> ⚠️ **已确认缺陷**：`L876` 的 `call choice choice [1][2][3]` 调用了一个**不存在的命令**
> （工程内只有 `input.bat`，没有 `choice.bat`）。CMD 会报 "命令不存在"，
> `choice` 变量保持为空，于是 `L877`、`L878` 的判断全部不成立，
> 直接落到 `L879 goto UNLOCKBL-DONE`。**用户"确认解锁"的交互形同虚设**。
> 正确写法应为 `call input choice [1][2][3]`。

---

### 2.5 ODM-2 方案（`L880`–`L896`）：最简单

```bat
1. chkdev fastboot
2. info fastboot → 已解锁则跳过
3. mzbox fbreadinfo → 取 mzbox__fbreadinfo__sn
4. fastboot.exe oem unlock:%mzbox__fbreadinfo__sn%    ← 直接用 SN 当解锁凭证
5. info fastboot 验证
6. 成功则 write fastboot misc misc_wipedata.img + reboot
```

> ⚠️ **已确认缺陷**：`L887` 写的是 `goto UNLOCKBL-ODM2`，但标签定义是
> `:UNLOCKBL-ODM-2`（`L880`）—— **少了一个连字符**。
> CMD 中 `goto` 到不存在的标签会**直接终止整个批处理进程**，
> 所以 odm-2 机型只要读 SN 失败，脚本就静默崩溃，用户看不到任何报错。
> 这是全工程危害最高的单个 bug。

---

### 2.6 ODM-NOTE8 方案（`L897`–`L925`）：必须还原

note8 没有 `flashing unlock` 可用，只能**刷入解锁版 aboot**（引导程序）来获得临时解锁状态，
解锁完成后**必须把原 aboot 刷回去**，否则设备无法正常启动。

```
1. chkdev qcedl → write qcedlsendfh
2. read qcedl aboot    bak\aboot_<ts>.img    noprompt   ★ 备份主
3. read qcedl abootbak bak\abootbak_<ts>.img noprompt   ★ 备份备
4. write qcedl aboot    res\<p>\aboot_unlock.img        ★ 刷解锁版（主）
5. write qcedl abootbak res\<p>\aboot_unlock.img        ★ 刷解锁版（备）
6. chkdev fastboot → reboot fastboot fastboot chk
7. info fastboot → 已解锁则跳到还原
8. fastboot.exe oem unlock                              ← 无需参数
9. call choice choice [1][2][3]                         ← 同样有 BUG
── 还原阶段 ──
10. 提示无需等开机，直接再进 9008
11. write qcedlsendfh
12. write qcedl aboot    bak\aboot_<ts>.img             ★ 还原主
13. write qcedl abootbak bak\abootbak_<ts>.img          ★ 还原备
14. reboot qcedl system
```

> 这是唯一一个"**必须 restore**"的流程。aboot 和 abootbak 是互备关系，
> 两个都要刷解锁版（否则设备可能从未损坏的那份启动），也都要还原。

### 2.7 上锁 BL（`:LOCKBL`，`L930`–`L977`）

上锁比解锁简单得多，但**风险更高**：

```bat
1. 显示警告（L940-955）：会格式化所有数据、可能无法开机、不恢复官方系统会变砖
2. pause 确认
3. chkdev fastboot
4. info fastboot → 若已上锁则提示无需重复
5. ★ 二次确认（L964-L970）：
   ECHO.1.暂不上锁   2.确定上锁
   call input choice #[1][2]        ← 默认「暂不上锁」（#后是默认值）
   if "%choice%"=="1" goto MENU
6. call write fastboot misc tool\Android\misc_wipedata.img    ← 先写清数据标记
7. fastboot.exe oem lock                                      ← 再上锁
8. call reboot fastboot system
```

**两个设计细节**：

1. **`#` 默认值**：`input choice #[1][2]` 里 `#` 后面的第一个选项是默认值，
   用户直接回车等于选 `1.暂不上锁`。危险操作的默认值设成"取消"，这是正确的。
2. **先 misc 后 lock** 的顺序不能反：如果先 `oem lock`，设备立刻进入
   "已上锁但数据未清"的状态，部分机型会拒绝启动甚至无法进入 Fastboot。
   先写 misc 标记能保证下次启动必定进 recovery 清数据。

## 3. 9008 刷机与备份

### 3.1 9008 通信的分层结构

9008（EDL, Emergency Download）模式的通信是分四层的，**理解这个分层是理解全部刷机功能的关键**：

```
┌────────────────────────────────────────────────────────────┐
│ L4  业务层   主脚本 UNLOCKBL / EDLFLASHFULL / ROOT / ...     │
├────────────────────────────────────────────────────────────┤
│ L3  编排层   write.bat / read.bat / partable.bat            │
│              qcedl（单分区）· qcedlxml（多 XML 整包）         │
├────────────────────────────────────────────────────────────┤
│ L2  协议层   ★ 这一段全工程只有三处，是核心                    │
│              ① QSaharaServer.exe  -s 13:<programmer>        │
│                 把引导程序推入设备，设备从 Sahara 切到 Firehose │
│              ② qcedlcmdhelper.exe -m sig -d <授权码>         │
│                 向 Firehose 出示签名，取得读写权限            │
│              ③ fh_loader.exe                                 │
│                 执行 configure / program / read 命令          │
├────────────────────────────────────────────────────────────┤
│ L1  设备层   Qualcomm HS-USB QDLoader 9008 (COMx)           │
└────────────────────────────────────────────────────────────┘
```

### 3.2 发送引导（`write.bat:L23-L134`）

**入口**：`call write qcedlsendfh <端口> <引导文件> <configuremode>`

三个参数的含义：
- `端口`：`auto` 或数字（`chkdev__port__qcedl`）
- `引导文件`：通常是 `res\<product>\devprg`
- `configuremode`：`ufs` / `emmc` / `spinor` / `auto` / `skip`

#### 步骤 1：Sahara 推引导（`L52-L61`）

```bat
QSaharaServer.exe -p \\.\COM<port> -s 13:<文件完整路径>
```

`-s 13:` 是 Sahara 协议的 **image ID 13**（= Firehose programmer）。
输出做两路判定：

```bat
find "File transferred successfully"   → 成功，正常继续
find "[portstatus]firehose"            → 设备已在 firehose，跳过（幂等）
否则 → goto QCEDLSENDFH-FAILED 重试
```

#### 步骤 2：探测是否需要授权（`L62-L69`）

```bat
fh_loader.exe --port=\\.\COM<port> --nop --mainoutputdir=<tmp> --skip_configure --noprompt
find "Authenticate failed" <输出>  → 需要授权
否则 → 不需要，跳过
```

`--nop` 是**空操作**（no operation）—— 只是让 fh_loader 试连接一次，
通过它的返回信息判断设备是否要求签名。这是个巧妙的"探针"用法。

#### 步骤 3：发送签名（`L70-L82`）

```bat
qcedlcmdhelper.exe -p COM<port> -m sig -d <512字符授权码>
find "Authenticate success"  → 成功
否则 → 重试（goto QCEDLSENDFH-MEIZU，重新走 Sahara）
```

> **注意重试目标**：失败后回到 `MEIZU`（`L82`）而不是 `MEIZU-1`，
> 即**重新发一次引导再试签名**。因为签名失败后设备可能已退回 Sahara 态。

#### 步骤 4：configure 端口（`L87-L134`）★ 全工程最精巧的重试逻辑

Sahara 发完引导后，设备处于 Firehose 但**存储未初始化**，必须先发 `<configure>` 命令。

**`auto` 模式的三次盲试**（`L91-L98`）：

```bat
call :qcedlsendfh-configure-run ufs     → 成功则结束
call :qcedlsendfh-configure-run emmc    → 成功则结束
call :qcedlsendfh-configure-run spinor  → 成功则结束
三次都失败 → 警告"设备可能无法正常读写"，继续（不中止）
```

**单次 configure 的 XML**（`L109-L112`）：

```xml
<?xml version="1.0" ?>
<data>
<configure MemoryName="ufs" Verbose="0" AlwaysValidate="0"
           MaxDigestTableSizeInBytes="8192"
           MaxPayloadSizeToTargetInBytes="1048576"
           ZlpAwareHost="1" SkipStorageInit="0" />
</data>
```

**自适应重试的四个分支**（`L114`–`L131`）—— 这段按 `port_trace.txt` 的报错信息
**动态改 XML 参数再重试**，最多 5 次：

| 设备报错 | 自动修正动作 | 代码 |
|---|---|---|
| `Host wants to send a Hash table 8192 larger than supported 0` | 删掉 `MaxDigestTableSizeInBytes` 参数 | `L120` sed 删除 |
| `ERROR: Tool doesn't come from ZTE.` | 给 configure 加 `Oem="ZTE"` | `L121` sed 插入 |
| `Host's payload to target size is too large` | 从 trace 里读出设备支持的 `MaxPayloadSizeToTargetInBytesSupported`，替换进 XML | `L122-L130` |
| 其他 | 判失败 | `L131` |

成功判定（`L117`）：

```bat
if "%errorlevel%"=="0" (find "Got the ACK for the <configure>" port_trace.txt && set result=y && goto :eof)
```

> **这是全工程最值得学习的一段**：不是简单重试，而是**解析失败原因 →
> 针对性地改参数 → 再试**。三种已知的设备差异都被自动适配了。
> 新工程应当把这个模式做成通用的"协议自协商"。

> ⚠️ **已确认缺陷**：`L114` 的 `set /a num+=1` 用的是**未初始化**的 `num`，
> 而 `L108` 初始化的是 `set n=0`（变量名不一致！）。如果环境中残留 `num` ≥ 5，
> 首次尝试就会撞上 `L119` 的"重试次数过多"。同时 `L30` 无条件
> `set configuremode=%storagetype%` 会覆盖调用方传入的第 4 参数，
> 使 `auto` 盲试分支实际上不可达。

### 3.3 单分区刷写：`write qcedl`

**入口**：`call write qcedl <分区名> <镜像路径> <端口> [引导路径]`
**实现**：`bin__write.bat:L422-L465`

这是"刷任意分区"的核心。完整流程：

```bat
① 检查文件存在，提取文件名和目录                          L429-432
② simg_dump.exe -f <镜像> -m basicinfo 探测是否 sparse      L435
   └─ 能解析 → sparse=true，否则 sparse=false
③ 端口 auto 则 chkdev qcedl                                L437-439
④ write qcedlsendfh <端口> <引导> auto                      L442   ← 发引导+配置
⑤ info qcedl <端口>                                         L444   ← 读设备信息
⑥ 校验 info__qcedl__portstatus == "firehose"                L445   ← 见缺陷说明
⑦ 循环探测每个 LUN 的分区表找到目标分区：                     L449-457
     for num = 0 .. lunnum-1:
       partable readgpt qcedl <存储类型> num gptmain <tmp>\gpt_main<num>.bin noprompt <端口>
       gpttool.exe -p gpt_main<num>.bin -f print:default:#insl:sector:10 -o output.txt
       for /f "tokens=4,5 delims= " ... find " <分区名> "
         → parstartsec = 第4列（起始扇区）
         → parsizesec  = 第5列（扇区数）
       找不到就 num+=1 继续下一个 LUN
⑧ 生成单条 program XML 写入 tmp\tmp.xml                    L461
⑨ call write qcedlxml <端口> <存储类型> <镜像目录> tmp.xml   L462
```

**第 ⑧ 步生成的 XML**（`L461`）—— 这是理解单分区刷写的钥匙：

```xml
<?xml version="1.0" ?>
<data>
<program filename="boot.img"
         physical_partition_number="0"
         label="boot"
         start_sector="123456"
         num_partition_sectors="65536"
         SECTOR_SIZE_IN_BYTES="4096"
         sparse="false"/>
</data>
```

> **为什么必须生成 XML 而不是直接用 fh_loader 的某个"分区"参数？**
> 代码注释说得很清楚（`L460`）："由于部分设备只能使用 xml 刷入，故生成 xml"。
> fh_loader 本身没有"按分区名刷写"的能力，它只认 XML 里描述的
> **物理位置**（LUN + 起始扇区 + 扇区数）。所以必须先从 GPT 里查出这些物理参数。

**分区名 → 物理位置的解析链**（第 ⑦ 步，全工程复用最多的一段）：

```
gpt_main<n>.bin  ←  partable readgpt 从设备回读 GPT 头+分区表
        ↓
gpttool.exe -f print:default:#insl:sector:10
        ↓
解析出文本表格，`tokens=4,5 delims= ` 取第 4、5 列 = 起始扇区、扇区数
```

`print:default:#insl:sector:10` 这个格式串的含义：默认格式、`#` 开头行、
以**扇区**为单位、宽度 10 列输出。用 `find " <分区名> "`（前后带空格）精确匹配，
避免 `boot` 误匹配 `bootloader`。

> ⚠️ **已确认缺陷**：`L445` 检查 `info__qcedl__portstatus` 是否为 `firehose`，
> 但 `info.bat:L44` 无条件 `set portstatus=firehose`（探测代码全被注释），
> 所以**这个保护永远通过**，等于没有校验。

### 3.4 单分区回读：`read qcedl`

**入口**：`call read qcedl <分区名> <保存路径> <notice|noprompt> <端口> [引导]`
**实现**：`bin__read.bat:L71-L113`

结构几乎和 write 对称，只有两处不同：

```bat
①~⑦ 与 write qcedl 完全一致（同样的 GPT 探测循环）
⑧ 生成 XML —— 注意 filename 是「空字符串」而不是实际文件名：   L109
   <program filename="<目标文件名>" physical_partition_number=".."
            label=".." start_sector=".." num_partition_sectors=".."
            SECTOR_SIZE_IN_BYTES=".." sparse="false"/>
⑨ call read qcedlxml <端口> <存储类型> <保存目录> tmp.xml      L110
```

**关键差异：`--convertprogram2read`**

`read qcedlxml` 调用 fh_loader 时多了一个开关（`bin__read.bat:L146`）：

```bat
fh_loader.exe --port=\\.\COM<port> --memoryname=<mem> --sendxml=<xml>
              --convertprogram2read     ★ 这个
              --mainoutputdir=<目录> --skip_configure
              --showpercentagecomplete --noprompt
```

> `--convertprogram2read` 让 fh_loader **把 `<program>` 指令反过来执行**：
> 原本是"把文件写到设备指定位置"，变成"把设备指定位置读出来写成文件"。
> 所以 **写和读共用同一套 XML 结构**，只是 flag 不同。
> 这是高通 QFIL 工具链的隐藏功能，也是本工程能用一个 XML 模板搞定双向传输的原因。

### 3.5 整包刷写：`write qcedlxml`

**入口**：`call write qcedlxml <端口> <存储类型> <搜索目录> <xml列表> [引导]`
**实现**：`bin__write.bat:L310-L373`

这是"9008 线刷救砖包"的核心。`xml列表` 是**斜杠分隔的多文件路径**，
例如：`rawprogram0.xml/patch0.xml/rawprogram1.xml/patch1.xml/...`

**处理流程**（`L319`–`L373`）：

```
① 清空 tmp\qcedlxml 并重建
② 按 / 切分 xml 列表，逐个处理（L326-L346）：
     for 每段:
       if 文件在 searchpath 下 → 用 searchpath\文件名
       elif 文件本身就是路径   → 直接用
       else → FATAL 找不到
       用 busybox cp 复制到 tmp\qcedlxml\<num>.xml      ← 注意用 busybox 而非 copy
       ★ qcedlxmlhelper.exe -f <xml> -m formatxml -o <xml>
          成功 → 这是 rawprogram，做自定义处理后加入列表
          失败 → 说明不是 rawprogram（如 patch.xml），直接原样加入列表
       拼成逗号分隔的新列表 xml_new
③ 发引导 + 识别存储类型（若为 auto）
④ :qcedlxml-flash-run 统一执行（L375-L380）
```

**清空重建 + busybox cp 的意义**：

- 清空：避免上一次刷机的残留 XML 混入本次
- `busybox cp` 替代 `copy`：代码注释明确说"此处 copy 命令经常失败, 可能是电脑环境原因"（`L336`）
  —— 这是**踩过坑之后的经验性替换**，很值得直接继承

**最终执行**（`L380`）：

```bat
fh_loader.exe --port=\\.\COM<port> --memoryname=<mem> --search_path=<目录>
              --sendxml=<逗号分隔的多个xml>
              --mainoutputdir=<tmp> --skip_configure
              --showpercentagecomplete --noprompt
```

> `--sendxml` 可以**接受逗号分隔的多个 XML 文件**，fh_loader 会依次执行。
> 这就是"一次命令刷完整个包"的原理，不需要每条 XML 调用一次。

**三类"部分失败"的容错**（`L382`–`L413`）—— 这段很有意思：

刷完后扫 `port_trace.txt`，把**可容忍的失败**挑出来只警告、不中止：

| trace 里的关键字 | 含义 | 处理 |
|---|---|---|
| ` Couldn't find the file ` | XML 里列了某个文件但目录里没有 | 警告并列名，跳过继续 |
| ` Failed to parse sparse file. Skip flashing: ` | sparse 镜像格式损坏 | 警告并列名，跳过继续 |
| ` Filesize is 0 bytes. ` | 文件是 0 字节 | 警告并列名，跳过继续 |

解析用的是 `setlocal enabledelayedexpansion` + `!line!` 延迟展开（`L385-L390`），
因为要在 `for` 循环里对循环变量再做一次 `for /f` 切分 —— 这是 CMD 里唯一可行的写法。

> **为什么需要这个**：官方 9008 包里经常带着空文件占位（比如空的 `devinfo.img`），
> QFIL 会跳过它们，但 fh_loader 会报错。这段代码就是在模仿 QFIL 的宽容度。

### 3.6 整包刷写主流程：`EDLFLASHFULL`（`L588`–`L684`）

**用户入口**：主菜单 `4`

#### 组装 XML 列表（`L607`–`L663`）

根据 `storagetype` 分两条路：

**UFS（多 LUN）**，`L617`–`L654`：循环 LUN 0 到 5，每个 LUN 找：

```bat
rawprogram<N>.xml  或  rawprogram_unsparse<N>.xml    ← 二者取其一
patch<N>.xml                                         ← 可选
```

任一 LUN（0~5）缺少 rawprogram → `goto EDLFLASHFULL-FILENOTFOUND` 重选目录。

> ⚠️ **设计过于严格**：UFS 设备不一定有 6 个 LUN，但代码要求 LUN 0-5 全部存在
> rawprogram 文件。实际魅族包里通常只有 `rawprogram0.xml` 到 `rawprogram4.xml`，
> 第 6 个不存在就会报"缺文件"。这是硬编码 LUN 数量带来的问题。

**EMMC（单 LUN）**，`L655`–`L663`：

```bat
rawprogram0.xml / rawprogram_unsparse.xml / rawprogram_unsparse0.xml  三选一
patch0.xml  可选
```

#### 执行（`L664`–`L682`）

```bat
1. 显示将使用的 xml 列表
2. chkdev qcedl rechk 1
3. start framework logviewer start    ← 开实时日志监控窗口
4. write qcedlsendfh <端口> <引导> auto
5. ★ write qcedlxml <端口> <存储类型> <目录> <xmls>
6. ★ mzbox edlsetbootablestoragedrive <端口> <存储类型>    ← 设置可引导存储盘
7. framework logviewer end
8. 询问 1.重启开机  2.清数据并开机
   选 2 → write qcedl misc misc_wipedata.img
9. reboot qcedl system
```

**第 6 步 `setbootablestoragedrive` 是刷机成败的关键**（`bin__mzbox.bat:L275` 起）：

```xml
<setbootablestoragedrive value="1"/>   <!-- 或 2 -->
```

UFS 设备有多个 LUN，刷完后必须告诉 bootloader "从哪个 LUN 启动"。
- `ufs` → value=1
- `emmc` → value=2

> 如果漏了这一步，设备会刷机成功但**无法启动**（找不到 boot 分区）。
> 这是 9008 刷机最常见的"刷完了但不开机"的原因之一。

### 3.7 整包备份：`EDLREADALLPAR`（`L378`–`L408`）→ `mzbox edlreadall`

> **GPT 扇区数的 6/34 与 5/33 之谜**：
> - 6 / 5 用于 4096 字节扇区（UFS）：GPT 头占 1+5=6 扇区，备份占 5 扇区

>

> 表示"磁盘总扇区数减去 N"。注意末尾那个点号是语法的一部分，不能省。

> **`filename=""` 的意义**：`L249` 生成空 filename 记录，用于把该分区

> 所以备份包虽然包含 persist.img，但刷回去时必须排除它。

### 3.8 刷写/回读任意分区（`WRITEPAR` / `READPAR`）

这两个是给高级用户的手动工具，**支持 5 种设备模式**，是全工程最灵活的入口。

#### 刷入任意分区（`:WRITEPAR`，`L1025`–`L1050`）

```
循环（输入 exit 退出）:
  ① 输入分区名
  ② if imgfolder 为空 → 设为工具箱上级目录（记住上次选择）
  ③ 选镜像文件 → 记住 sel__file_folder 供下次用
  ④ ★ call chkdev all            ← 自动识别当前设备在哪个模式
  ⑤ if 模式是 qcedl → write qcedlsendfh  ← 只有 9008 需要发引导
  ⑥ ★ call write %chkdev__mode% <分区名> <文件> <端口>
  ⑦ if 模式是 qcedl → reboot qcedl qcedl   ← 不重启系统，留在 9008 方便连续操作
  ⑧ 回到 ①
```

**第 ⑥ 步是全工程最优雅的设计**：

```bat
call write %chkdev__mode% %parname% %sel__file_path% %chkdev__port__qcedl%
```

`%chkdev__mode%` 的值直接就是 `write.bat` 的子命令名！
`chkdev` 探测到 `system` → 调用 `write system`；探测到 `fastboot` → `write fastboot`；
探测到 `qcedl` → `write qcedl`。

于是同一行代码自动适配 **5 种传输通路**：

| 模式 | write 子命令 | 底层实现 |
|---|---|---|
| `system` | `write system` | adb push + su + `dd if=.. of=<分区路径>` |
| `recovery` | `write recovery` | adb push + `dd`（TWRP 自带 root） |
| `fastboot` | `write fastboot` | `fastboot flash <分区> <文件>` |
| `fastbootd` | `write fastbootd` | 同上 |
| `qcedl` | `write qcedl` | 发引导 + GPT 探测 + XML + fh_loader |

> **第 ⑦ 步的取舍**：刷完后 `reboot qcedl qcedl`（9008 软重启回 9008），
> 而不是重启进系统。这样用户能**连续刷多个分区**而不用每次重新进 9008。
> 这是很贴心的可用性设计。

#### 回读任意分区（`:READPAR`，`L996`–`L1022`）

```bat
① 选保存目录（只选一次）
循环:
  ② 输入分区名 → 保存为 <目录>\<分区名>.img
  ③ call chkdev all
  ④ if qcedl → 发引导
  ⑤ call read %chkdev__mode% <分区名> <保存路径> notice <端口>
  ⑥ if qcedl → reboot qcedl qcedl
```

同样用 `%chkdev__mode%` 做分发，支持 5 种通路。差异：

- `system` 模式下 `read` 会走 `dd if=<分区路径> of=./sdcard/<分区>.img`，
  再用 `adb pull` 拉回来，然后**删除手机上的临时文件**（`bin__read.bat:L183-L196`）
- 系统模式需要 Root，代码在 `L176-L179` 用 `echo.su > cmd.txt` 探测

## 4. 基带备份（QCN）

### 4.1 QCN 是什么、为什么要单独备份

**QCN**（Qualcomm Calibration Network）是高通平台承载**基带校准数据**的文件，包含：

- IMEI / MEID（设备唯一识别码）
- 射频校准参数（每个设备独有，出厂时逐台校准）
- 网络参数

> **为什么不能靠"全分区备份"覆盖**：QCN 不在普通分区里，它存在
> **modemst1 / modemst2 / fsg** 这几个分区，但 QCN 工具读写的是
> 高通基带处理器内部的 EFS 文件系统，**走的是完全不同的通道（DIAG），不是 EDL**。

所以 QCN 备份必须让设备进入 **qcdiag 模式**（高通基带调试口），
用 `QCNTool.exe` 通过 DIAG 协议读写，而不是 fh_loader。

### 4.2 进入 qcdiag 模式（用户侧）

参考实现里的说明（`煤油工具箱.bat:L145-L149`）：

```
魅族开启高通基带调试端口方法:
  1. 开机状态开启 USB 调试
  2. 打开拨号
  3. 输入 *#*#88#*#* , 弹出选项后选 QPST
  4. 如果没有弹出选项, 则重新输入 *#*#3838664#*#* , 选 usb mode 再选 QPST
```

> `*#*#88#*#*` = `*#*#88#*#*`，`88` 对应 QPST 菜单。
> `3838664` = "DUMMY" 的九宫格数字映射（3=D,8=U,3=D,8=U... 实际是 `DUMMY` 的 T9 编码）。

### 4.3 设备检测（`chkdev qcdiag`）

`bin__chkdev.bat:L35` 定义模式，`L60` 定义匹配规则：

```bat
if "%mode%"=="qcdiag" set chktype=port& set modename=高通基带调试模式

:: 匹配规则（L60）—— 覆盖多种厂商的 DIAG 端口名
devcon.exe listclass Ports 2>&1 | busybox egrep -n
  "Qualcomm HS-USB Android DIAG 901D|Qualcomm HS-USB Diagnostics|
   Qualcomm HS-USB MDM Diagnostics|ZTE Handset Diagnostic Interface|
   LGE Mobile USB Diagnostic Port|USB Diagnostics Port"
  | find /n ":" 1>%tmpdir%\output.txt
```

> 注意这里**不只匹配 Qualcomm**，还兼容 ZTE / LG / 通用 DIAG 端口名 ——
> 说明作者遇到过各种驱动版本的端口命名差异。

端口号提取同 9008（`L68-L70`）：

```bat
busybox.exe sed -i "s/ /\r\n/g" output.txt
for /f "tokens=1 delims=(COM) " %%a in ('type output.txt ^| find "(COM"') do set port=%%a
```

### 4.4 QCN 备份（`read qcdiag`）

**入口**：主菜单 `16` → 子菜单 `1` → `:QCN-READ`（`煤油工具箱.bat:L159`）

```bat
:QCN-READ
ECHOC 请开启高通基带调试端口...
call chkdev qcdiag rechk 1                    L160   等待用户进入 DIAG 模式
for /f %%a in ('gettime.exe') do set baktime=%%a
ECHO.备份QCN到 bin\res\%product%\bak\qcnbak_%baktime%.qcn . 耗时较长, 请耐心等待...
call read qcdiag %chkdev__port__qcdiag% res\%product%\bak\qcnbak_%baktime%.qcn
```

**`read qcdiag` 实现**（`bin__read.bat:L43-L68`）—— 很短，核心就一条命令：

```bat
① 分解 filepath 为 目录 + 文件名                        L51-L54
② 检查目录存在、文件已存在则提示覆盖                      L55-L56
③ 端口 auto 则 chkdev qcdiag                            L58-L59
④ ★ QCNTool.exe -r -p <端口> -f <目录> -n <文件名>        L62
⑤ 输出存到 tmp\output.txt，并追加到日志                  L63-L64
⑥ ★ 校验关键字 "Reading QCN from phone... OK"            L65
   没有 → 报错 + pause + 重试（goto QCDIAG-1）
```

**`QCNTool.exe` 的参数**：

| 参数 | 含义 |
|---|---|
| `-r` | read（备份）。恢复时用 `-w` |
| `-p <端口>` | COM 口号（数字，不带 `COM` 前缀） |
| `-f <目录>` | QCN 文件所在**目录**（不是文件路径） |
| `-n <文件名>` | QCN **文件名**（不含目录） |

> 注意 `-f` 和 `-n` 分开传：这是很多高通工具的惯例，容易写错成 `-f <完整路径>`。

### 4.5 QCN 恢复（`write qcdiag`）

```bat
:QCN-WRITE
ECHOC 请选择要恢复的QCN文件...
call sel file s %framework_workspace%\res\%product%\bak [qcn]      ← 只能选 .qcn
ECHOC 请开启高通基带调试端口...

ECHO.恢复QCN. 耗时较长, 请耐心等待...
call write qcdiag %chkdev__port__qcdiag% %sel__file_path%
```

**`write qcdiag` 实现**（`bin__write.bat:L137-L157`）：

```bat
① 检查 qcn 文件存在
② 端口 auto 则 chkdev qcdiag
③ ★ QCNTool.exe -w -p <端口> -f <完整文件路径>             L151
④ ★ 校验关键字 "Writing Data File to phone... OK"          L154
```

> **两个方向的参数格式不一致**：读的时候 `-f 目录 -n 文件名`，
> 写的时候 `-f 完整文件路径`。这是 `QCNTool.exe` 自身的设计，不是笔误。

### 4.6 一个重要的安全提示

两处实现都有这行注释（`bin__read.bat:L63`、`bin__write.bat:L152`）：

```bat
::注意: 原始输出中包含设备IMEI, 如不希望将原始输出保存到日志, 请将下面一行type命令注释掉
type %tmpdir%\output.txt>>%logfile%
```

> **QCNTool 的原始输出里含 IMEI**，而参考实现默认**把它写进日志文件**。
> 日志轮转保留 6 份，意味着历史 IMEI 会长期留在磁盘上。
> **新工程应当默认脱敏或默认不记录**，这是隐私问题。

## 5. 四条链路共用的底层协议

### 5.1 端口探测（`chkdev`）的通用模式

所有需要 COM 口的模式（`qcedl` / `qcdiag` / `sprdboot` / `mtkbrom` / `mtkpreloader`）
共用 `:chkport`（`bin__chkdev.bat:L51-L74`）：

```
for 尝试次数:
  devcon.exe listclass Ports | busybox egrep -n "<关键字>"   → output.txt
  检查 output.txt 里 [1] 是否有（= 恰好一个设备）
    没有 → 次数+1，继续
    有 [2] → 报"多个设备"，pause 后重试     ← 防止选错设备
    有 [1] → 提取 COM 号
busybox sed 把空格换成换行
for /f "tokens=1 delims=(COM) " 截取 COM 前的内容
```

> **"必须恰好一个设备"的检查很关键**：同时插两个 9008 设备时，
> 选错端口刷错机器是灾难性的。代码在 `L66` 用 `find "[2]"` 检测多个设备并阻断。

### 5.2 扇区大小与存储类型

三种存储类型的扇区大小不同，**影响所有 XML 的 `SECTOR_SIZE_IN_BYTES`**：

| storagetype | 扇区大小 | GPT 主/备扇区数 | 典型设备 |
|---|---|---|---|
| `emmc` | 512 | 34 / 33 | 魅族 16X、16Xs、note8、note9、X8 |
| `ufs` | 4096 | 6 / 5 | 魅族 16S 起绝大多数 |
| `spinor` | 4096 | 6 / 5 | 极少数（未在机型表出现） |

> `info qcedl` 会实测读出来（`bin__info.bat:L70-L113`），但那段代码因为
> `portstatus` 写死的缺陷**实际不可达**，最终靠 `write qcedlsendfh` 的
> `auto` 模式盲试 configure 来间接确定。

### 5.3 三种"重启"的语义差异

| 命令 | 含义 | 用途 |
|---|---|---|
| `reboot qcedl qcedl <端口>` | 9008 软重启，仍回 9008 | 连续操作同一台设备（免重插） |
| `reboot qcedl system <端口>` | 9008 → 正常开机 | 刷完收尾 |
| `reboot fastboot qcedl` | Fastboot → 9008 | 解锁流程中转 |
| `reboot fastboot fastboot chk` | Fastboot 重新进入并复核 | 刷新 Fastboot 状态 |

`reboot qcedl <目标>` 的实现在 `bin__reboot.bat:L139-L141`，
用 `<power value="reset"/>` 之类的 fh_loader XML。

## 6. 给新工程的实现建议

### 6.1 应当直接继承的机制

| 机制 | 位置 | 为什么值得继承 |
|---|---|---|
| **`%chkdev__mode%` 直接当子命令名分发** | `L1048` | 一行代码适配 5 种传输通路，极其优雅 |
| **512 字符定长校验用 `%var:~511,1%`** | `L358-L360` | 不用正则精确校验长度 |
| **configure 报错驱动的自适应重试** | `write.bat:L114-L131` | 解析失败原因→改参数→重试，真正的协议自协商 |
| **先删后写再判存在** | `L281-L286` | 避免"旧文件让新操作假成功" |
| **`busybox cp` 替代 `copy`** | `write.bat:L338` | 作者实测 `copy` 在某些环境不可靠 |
| **persist 分区强制排除** | `L406` | 覆盖 persist = 指纹/传感器永久损坏 |
| **`setbootablestoragedrive`** | `mzbox.bat:L275` | 漏了会"刷成功但不开机" |
| **`--convertprogram2read` 读写同构** | `read.bat:L146` | 一个 XML 模板搞定双向 |
| **危险操作默认值设为"取消"** | `L968` | `input choice #[1][2]` 的回车默认安全项 |
| **必须恰好一个设备的端口检查** | `chkdev.bat:L66` | 防刷错机器 |

### 6.2 必须在新工程修掉的缺陷

| # | 缺陷 | 位置 | 修法 |
|---|---|---|---|
| 1 | `call choice` 调用不存在的命令 | `L876`、`L914` | 改为 `call input choice` |
| 2 | `goto UNLOCKBL-ODM2` 标签少连字符 → 进程崩溃 | `L887` | 改为 `goto UNLOCKBL-ODM-2`；并改用函数化调用避免静默退出 |
| 3 | `info.bat` 里 `portstatus` 写死 → 四处保护失效 | `info.bat:L44` | 恢复探测逻辑，或移除失效的检查 |
| 4 | `slot.bat` 的 `& goto :eof` 短路 → 切槽位全失效 | `slot.bat:L56/L98/L146` | 加括号或用 `if ... ( ... ) else ( ... )` |
| 5 | `write.bat` 的 `configuremode` 被覆盖 | `write.bat:L30` | 只在参数为空时才用 `storagetype` 兜底 |
| 6 | `num` 未初始化导致 configure 偶发失败 | `write.bat:L108/L114` | 统一用 `num`，在函数开头 `set num=0` |

### 6.3 建议重新设计的部分

**① 把"人工换码"流程改为可插拔的授权服务**

现状：所有码都靠打开 kdocs 在线文档 + 人工。新工程建议：

```
定义接口：
  getDeviceId()      → 从设备读 chipid/socid（已有实现可复用）
  requestCodes(id)   → 可插拔：本地文件 / HTTP API / 人工输入
  importCodes(text)  → 解析 + 校验 + 落盘
```

这样既能兼容现在的"人工发码"，也能接自动化服务，还能支持离线导入。

**② 把私有的偏移写入做成数据驱动**

现状：`HexTool` 的四个偏移硬编码在代码里（`L828-L843`）。
建议抽到机型配置：

```yaml
meizu18:
  bl_unlock:
    scheme: auth-private
    patches:
      - { offset: 0x11000, len: 4,   data: "4C4F434B" }
      - { offset: 0x11004, len: 256, data: "$blunlockcode" }
      - { offset: 0x11104, len: 16,  data: "666163746F7279" }
      - { offset: 0x11114, len: 16,  data: "6D54657374332E31302E372E30" }
      # 需要时再加 0x14000 那一组
```

新机型适配就变成"加一段配置"，不用改代码。

**③ 明确区分"致命失败"和"可继续失败"**

现状：大量地方用 `pause` + 继续，用户无法判断当前是什么状态。
建议定义统一的结果语义：

| 级别 | 含义 | 行为 |
|---|---|---|
| `FATAL` | 无法继续，状态未知 | 中止 + 明确告知设备当前状态 + 恢复建议 |
| `RECOVERABLE` | 可重试 | 自动重试 N 次，失败后转 FATAL |
| `WARN` | 已跳过，不影响后续 | 记日志 + 继续 |
| `OK` | 成功 | 继续 |
