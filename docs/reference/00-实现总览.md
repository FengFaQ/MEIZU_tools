# 00 · 参考工程实现总览

> 分析对象：`煤油工具箱 1.2.1-beta9`（作者：酷安 @某贼，框架 BFF v1.5）
> 分析方式：解压 → GBK 转 UTF-8 → 逐文件精读（共 24 个 bat/csv 脚本，约 12,000 行）

---

## 1. 工程定位

一个**纯 Windows 批处理（.bat）实现**的魅族手机刷机工具箱。核心能力：

| 能力 | 说明 |
|---|---|
| 解锁 BL | 按机型方案构造解锁数据，写入 `private` 分区（9008 / Fastboot 双通路） |
| 获取 Root | 抓 boot → Magisk 修补 → 回写（按 Magisk 版本分支，共 17 套） |
| 刷 Recovery | TWRP 安装、instpatch |
| 9008 线刷 | 解析官方救砖包 XML，走 fh_loader Firehose |
| 全分区备份 | EDL 逐分区回读，含 persist 保护 |
| 任意分区读写 | 12 种传输通路统一封装 |
| 槽位管理 / QCN / 投屏 / 分区表 | A/B slot、基带备份、scrcpy、GPT 读写 |

技术栈上没有任何"框架"，全是 CMD 脚本 + 随包 exe 工具 + 一个自制的 shell-like 框架层（BFF）。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│ L0 入口层   煤油工具箱.bat / 命令行.bat / 驱动运行库.bat      │
├──────────────────────────────────────────────────────────┤
│ L1 框架层   framework.bat                                 │
│             startpre（30+ 项工具自检）· theme（7 套配色）    │
│             conf（配置读写）· log（日志轮转）                │
│             loadcsvconf（CSV→变量）· chkdiskspace · adbpre │
│             FATAL（统一错误出口）                            │
├──────────────────────────────────────────────────────────┤
│ L2 基础件   input（带白名单校验的输入）· sel（文件对话框）      │
│             calc（四则/单位换算/比较）· log · open · echo    │
│             random · scrcpy · reboot（跨模式重启编排）       │
├──────────────────────────────────────────────────────────┤
│ L3 业务模块 chkdev  设备模式探测                             │
│             write   12 种写通路                             │
│             read    5 种读通路                              │
│             info    设备信息（qcedl/adb/fastboot/分区/磁盘）  │
│             partable 分区表  · slot 槽位 · clean 格式化       │
│             imgkit  镜像处理 + Magisk 修补（170KB 主体）      │
│             dl      下载（蓝奏云解析）· mzbox 设备信息聚合     │
├──────────────────────────────────────────────────────────┤
│ L4 工具层   tool/Win/*.exe（adb fastboot fh_loader 等 26 个） │
│             tool/Android/*（推到手机的 ARM 二进制）           │
└──────────────────────────────────────────────────────────┘
```

**调用约定**（全工程一致的伪面向对象风格）：

```bat
call framework  startpre                 :: 模块名作为 $1，用 goto %args1% 分发
call write      qcedl <分区> <文件> <COM口>
call read       qcedl <分区> <文件> notice <COM口>
call chkdev     qcedl rechk 1            :: rechk = 复核，1 = 间隔秒数
call input      choice [1][2][A]#[默认]
call sel        file s <起始目录> [img][zip]
call calc       b2gb <输出变量名> nodec <字节数>
```

模块之间**只通过 `set` 的全局变量交换数据**，命名规范为 `<模块>__<子命令>__<字段>`：

```bat
chkdev__port__qcedl       ;; chkdev 探测到的 9008 端口号
chkdev__mode              ;; 当前设备模式
sel__file_path            ;; 选择的文件路径
info__adb__product        ;; adb 读到的设备代号
slot__cur                 ;; 当前槽位 a/b
calc__numcomp__result     ;; 比较结果 greater/less/equal
framework__chkdiskspace__enough
```

这是整个工程最核心的"接口设计"——**用变量命名空间替代返回值**。

## 4. 启动链（实测行号）

```
煤油工具箱.bat
 L5   chcp 936                              切 GBK 代码页（脚本本身是 GBK 编码）
 L6   cd /d %~dp0 → if exist bin (cd bin)   进入 bin 作为运行根
 L11  tool\Win\gap.exe %0 || EXIT           自提权到管理员（gap.exe 失败则退出）
 L14  call conf\fixed                       载入版本常量
 L15  if exist conf\user.bat call conf\user  载入用户态（上次选的机型/主题）
 L16  if exist conf\dev-%product%.bat call   载入机型配置
 L20  call framework theme %framework_theme% 载入配色变量
 L25  mode con cols=71                      固定窗口宽度（菜单排版依赖）
 L28  call framework startpre                ◀ 30+ 项工具可用性自检
 L34  product 为空 → goto SELDEV             未选机型先选机型
 L36  storagetype 为空 → goto SELDEV         机型数据缺失兜底
 L41  :MENU                                  主菜单
```

`framework startpre` 做的事（按顺序）：
1. 打印 ASCII art logo
2. 补 PATH：`%windir%\Sysnative`（关键！32 位进程访问 64 位系统目录）
3. 自检 find/findstr/copy/move/ren/del 六个系统命令
4. 检查路径中**不允许有空格或英文括号**（L127）—— 因为全脚本都不加引号
5. 把 `%cd%`、`tool\Win` 加入 PATH（所以脚本里直接写 `adb.exe`、`7z.exe`）
6. 检查 ECHOC/gettime 可执行
7. 建立 `tmpdir`、`logfile`，日志文件超过 `framework_lognum`(默认6) 个就删最老的
8. 逐个验证 26 个 exe 能跑（不是只查存在，而是**执行一次并 grep 输出特征串**）
9. 验证 6 个 Android ARM 二进制存在、qualcomm_config.py 存在

> 这一层是"防御式启动"的范本：**宁可启动慢 3 秒，也不要跑到一半才崩**。

## 5. 机型数据库设计（dev.csv）

CSV 是一张"机型 × 方案"矩阵，驱动所有业务分支：

| 列 | 含义 | 取值 |
|---|---|---|
| product | 设备代号 | `[16S]` `[meizu20]` `[MeizuVenus]`… |
| model | 市场名 | 魅族16S |
| cpu | SoC | 骁龙855 / 8Gen2… |
| storagetype | 存储类型 | `emmc` / `ufs` |
| **blplan** | **解锁方案** | `auth-private`(官方授权码) / `auth-mzkv-sig`(mzkv+签名) / `auth-mzkv-nosig` / `odm-1` / `odm-2` / `odm-note8` / `avb` |
| **parlayout** | **分区布局** | `aonly` / `ab` / `ab_rec` |
| **bootpar** | **Root 目标分区** | `boot` / `init_boot` |
| **edlplan** | **9008 进入方式** | `key`(按键) / `cmd`(命令) / `edlcable`(9008 线) / 空 |
| done | 适配状态标记 | |

**这三个字段就是整个分支逻辑的开关**：
- `blplan` → 决定解锁/授权码走哪套 scheme（主脚本 6 个 UNLOCKBL 分支）
- `parlayout` → 决定分区名是否加 `_a`/`_b` 后缀、是否要切槽位
- `bootpar` → Android 13+ GKI 设备用 `init_boot`，旧设备用 `boot`
- `edlplan` → 决定能否用命令进 9008，还是要用户按键

`dev-<product>.bat` 是 dev.csv 的**物化缓存**，由 `call mzbox confdevpre` 自动生成
（`bin__mzbox.bat.txt:L615`）：读 CSV 表头做变量名、按 `[product]` 行取值、逐条 `call framework conf` 写盘。
好处：业务脚本 `call conf\dev-xxx.bat` 即可，不用每次解析 CSV。

## 6. 核心业务流摘要

### 6.1 获取 Root（最典型的跨模块编排，`煤油工具箱.bat:L1081`）

```
:ROOT
  ├─ 选 Magisk 包（内置 29.0 / 自选 apk+zip）
  ├─ call chkdev system rechk 1        开机状态 + USB 调试
  ├─ call info adb                     读型号/安卓版本
  ├─ call slot system chk              读当前槽位 → 拼出 targetpar=boot_a
  │   ⚠ 校验 info__adb__product 与所选 product 是否一致（L1119，仅警告不阻断）
  │
  ├─[meizu20inf 特例]→ :ROOT-SELBOOT   用户手动提供 boot 镜像
  │      call imgkit magiskpatch → call reboot system fastboot
  │      call write fastboot boot <patched> → call reboot fastboot system
  │
  └─[常规]→ :ROOT-EDL
         call reboot system qcedl       或让用户按电源+音量
         call chkdev qcedl rechk 1
         call write qcedlsendfh …        发 Firehose 引导
         call read qcedl boot_a bak\…    先备份原分区（重要！）
         call imgkit magiskpatch …      修补
         call write qcedl boot_a …      回写
         call reboot qcedl system
  最后：adb install -r -t -d Magisk.apk
```

**结论**：Root 不是在 Windows 本地算出来的，而是 **"抓原分区 → 本地用 magiskboot 重打包 → 回写"**。
所以 `imgkit magiskpatch` 是整个工具箱技术含量最高、也是最脆弱的部分（170KB 里 90% 是它的版本分支）。

### 6.2 解锁 BL（`煤油工具箱.bat:L687`）

按 `blplan` 分六条路：

| blplan | 方案 | 特征 |
|---|---|---|
| `odm-1` | 无限制 | 直接 fastboot 解锁，无需授权码（L1713） |
| `odm-2` | 无限制（X8） | 同上变体（L880，含标签拼写缺陷，见 §7） |
| `odm-note8` | note8 专用 | 需要刷入 misc 镜像绕过后擦除 |
| `auth-private` | 官方授权码 | 读 chipid/socid → 校验 `blunlockcode.txt` + `edlauthcode.txt` → 进 9008 → 用 HexTool 把解锁标志按偏移写进 `private.img` 再回写（L1505） |
| `auth-mzkv-sig` | mzkv + 签名 | 导入 `mzkv_unlock.img` + 授权码（L1439） |
| `auth-mzkv-nosig` | mzkv 无签名 | 仅导入 mzkv（L1441） |

`auth-private` 的精髓在 L1669-L1685 的注释里：解锁信息是往 `private.img` 的固定偏移写多段标记。

```bat
::HexTool.exe %tmpdir%\private.img 00081920 4 4C4F434B             ; 偏移0x14000 写 "LOCK"
::HexTool.exe %tmpdir%\private.img 00081924 256 %blunlockcode%     ; 写解锁码
::HexTool.exe %tmpdir%\private.img 00082180 16 666163746F7279...   ; 写 "factory"
::HexTool.exe %tmpdir%\private.img 00082196 16 6D54657374332E...   ; 写 mTest3.10.7.0
```

> 这几行是"厂商私有协议"的核心知识，也是这类工具箱真正的价值所在。

### 6.3 设备模式探测（`chkdev.bat`）

全工程的"眼睛"，支持 10 种模式：

| mode | 探测手段 | 判定依据 |
|---|---|---|
| system / recovery / sideload | `adb devices -l` | 输出含关键字，且**只能有 1 个设备** |
| fastboot | `fastboot devices -l` | 含 `fastboot` |
| fastbootd | 同上 + `fastboot getvar is-userspace` | `is-userspace: yes` 才是 fastbootd |
| qcedl (9008) | `devcon listclass Ports` + `busybox egrep` | 匹配 `Qualcomm HS-USB QDLoader 9008` |
| qcdiag | 同上 | 匹配 `Android DIAG 901D` 等多种字符串 |
| sprdboot / mtkbrom / mtkpreloader | 同上 | 展讯/联发科端口名 |

**端口号提取**是个巧妙 hack（L68-70）：先用 `busybox sed` 把空格换成 `\r\n`，
再用 `for /f "tokens=1 delims=(COM) "` 截取 `(COM12)` 前面的数字。
`delims` 里放 `(COM)` 是**字符集分隔符**，即按 `(`、`C`、`O`、`M`、`)`、空格 任一分隔。

`rechk <秒>` 机制：检查一次 → `TIMEOUT /T n /NOBREAK` → 再检查一次。
用于"用户刚插上 USB，驱动需要 1 秒才枚举出来"的场景。

### 6.4 输入校验（`input.bat`）

主菜单的选项输入做了三层过滤（`bin__input.bat.txt:L30-34`）：
1. 不含 `"`；2. 不含空格；3. 不含 `~ ! @ # % ^ & * ( ) + = [ ] | : ; ' < > ,`
4. 必须在白名单 `[1][2][A]` 里

原因：**CMD 的变量展开是文本替换**，用户输入 `%` 或 `&` 会被二次解析成命令。
这是批处理工程里必须做的注入防护。

### 6.5 Magisk 修补机制（`imgkit.bat`，全工程技术含量最高处）

这是 3849 行里占 90% 的部分，也是最容易理解错的地方。三个关键事实：

**① 分支键不是版本号，而是 `boot_patch.sh` 的 MD5**

```bat
::imgkit.bat:L162
for /f "tokens=1 delims= " %%a in ('busybox.exe md5sum %tmpdir%\imgkit-magiskpatch\boot_patch.sh') do set bootpatchmd5=%%a
::L168 起 37 行 MD5 → 方案标签映射
if "%bootpatchmd5%"=="0d1bdb70f8ae72ff2fa646a8aff448b7" set bootpatchplan=ALPHA_070719db_28001
...
if "%bootpatchplan%"=="" … FATAL   ;; 未收录的 MD5 直接拒绝
```

脚本**从不调用**官方 `boot_patch.sh`，而是在批处理里手工复刻它的每一步
（unpack → cpio patch → dtb patch → kernel hexpatch → repack）。
复刻必须与那一版脚本逐条对齐，所以用 MD5 锁定上游脚本的**确切字节**。
37 行映射里有 2 组重复 MD5（L173/L174、L178/L179），实际 35 个唯一指纹，
收敛到 **18 套行为标签**，按语法代际压缩其实只有 **5 代**（G1 单体 magisk → G5 上古语法）。

**② MODE0 / MODE1 =「该镜像是否已被 Magisk 补过」**

判据是 `magiskboot cpio … test` 的返回码（L229/L230）：

```bat
if "%STATUS%"=="0" goto …-MODE0      ;; 原厂镜像
if "%STATUS%"=="1" goto …-MODE1      ;; 已补过 → 先 restore 再打
```

MODE1 先 `magiskboot cpio ramdisk.cpio "extract .backup/.magisk config.orig" "restore"`（L247）
把 ramdisk 还原成原厂态再打补丁 —— 这是**幂等性设计**，防重复修补叠加污染。
与"是否保留 ramdisk""bootctl""vendor_boot"均无关；无 ramdisk 时强制走 MODE0。

**③ boot / init_boot 的差异是真实的**

`dev.csv` 的 `bootpar` 只有 `boot` / `init_boot` 两值，`vendor_boot` 全工程零命中（不支持）。
GKI 机型补 `init_boot` 时该镜像**不含 kernel**，因此 G3–G5 的 kernel 补丁段在这类设备上不执行
—— 设计上无害，但需知情。

## 7. 设计评价

### 优点

1. **分层干净**：框架 / 基础件 / 业务 / 工具四层，业务脚本只管业务流程，不碰底层细节。
2. **接口统一**：`call <模块> <子命令> <位置参数>` + 命名空间变量，等价于函数调用约定。
3. **数据驱动**：机型差异全在 `dev.csv` 一行里，加机型=加一行+放引导文件，不改代码。
4. **防御式启动**：26 个工具逐个"执行+校验输出"，一次把环境问题全暴露。
5. **日志完善**：每次运行独立日志、自动轮转、关键操作随手写日志。
6. **有恢复路径**：Root 前先备份原分区，并专门提供"Root 不开机恢复"菜单（`222`）。
7. **危险提示到位**：`meizu20inf` 切换槽位会变砖，主菜单顶部常驻红色警告（L53）。

### 缺陷（本次分析中实证发现）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **设备名与资源目录名不一致** | `dev.csv:L30` 用 `[MeizuVenus]`，资源目录是 `res\meizulucky08\` | Lucky08 的 `res\%product%\devprg` 找不到 → 该机型 9008 全链路失效 |
| 2 | **未加方括号的机型对用户不可见** | `dev.csv:L27` `note16pro,`、`L28` `pro7,`；选机型界面用 `find "["` 过滤（主脚本 `L1167`） | 这两个机型在列表里根本不出现（28 行数据只有 26 条可选） |
| 3 | **空属性机型形成死循环** | `pro7` 行只有名字无属性；`L36` 判 `storagetype` 为空就 `goto SELDEV` | 即使能选中也被弹回选机型界面 |
| 4 | **`call choice` 命令不存在** | 主脚本 `L876`/`L914` 调 `call choice choice [1][2][3]`，而工程内只有 `input.bat`，无 `choice.bat` | ODM 解锁的确认交互失效，`choice` 变量为空 |
| 5 | **标签名拼写错误导致崩溃** | `L880` 定义 `:UNLOCKBL-ODM-2`，`L887` 却 `goto UNLOCKBL-ODM2`（少一连字符） | odm-2 机型 Fastboot 读 SN 失败时脚本直接终止 |
| 6 | **`goto` 失败会杀死进程** | CMD 语义：`goto` 到不存在的标签直接终止批处理 | 全工程 `goto FATAL` 式兜底对"标签写错"完全无效（缺陷 5 即实例） |
| 7 | **`portstatus` 写死为 firehose** | `info.bat:L44` 无条件 `set portstatus=firehose`，探测代码 L36-L43 全被注释 | write/clean/mzbox/slot 四处"端口未就绪"保护永远假通过；`info` 里 44 行存储类型实测代码（L46-L113）不可达 |
| 8 | **`&` 短路使切槽位整体失效** | `slot.bat:L56/L98/L146` 的 `if not "%func%"=="set" ENDLOCAL & … & goto :eof` 中 `goto :eof` 恒执行 | `:SET-ADB/-FASTBOOT/-QCEDL` 永不可达，切槽位三种模式全失效 |
| 9 | **`write.bat` 参数被覆盖** | `write.bat:L30` 无条件 `set configuremode=%storagetype%`，覆盖 L27 收到的第 4 参数 | auto 盲试分支成死代码；叠加 `L114` 用未初始化 `num` 做重试计数 → 偶发"首轮即判重试超限" |
| 10 | **`pause` 漏括号致无人值守卡死** | `imgkit.bat:L1850` `if not "%mode%"=="noprompt" … & pause>nul` 少了外层括号 | `noprompt` 下仍暂停；主脚本 `L1142` 正是带 `noprompt` 的自动 Root 链，修补前后大小不等就卡住 |
| 11 | **缺 ramdisk 守卫会死循环** | `18100`/`17200` 分支未判断 `ramdisk.cpio` 是否存在 | GKI 无 ramdisk 镜像进入无限重试 |
| 12 | **Magisk 版本硬编码** | `imgkit.bat` 3849 行，L168-L204 是 `boot_patch.sh` MD5 → 18 套方案标签，L209+ 展开 | 新 Magisk 版本必须改代码；自选 Magisk 包 MD5 未收录即 `FATAL` |
| 13 | **全脚本不加引号** | `framework.bat:L127` 直接禁止路径含空格/括号 | 放在 `C:\Program Files\` 或带空格目录直接启动失败 |
| 14 | **无一致性校验** | 型号不匹配仅警告（主脚本 `L1119`） | 选错机型仍可刷入，有变砖风险 |
| 15 | **`ECHOC.exe` 依赖** | 彩色输出全靠自制 exe | 杀软易误报（此类工具箱被误杀的常见原因） |

## 8. 对"新魅友工具箱"的启示

| 参考工程的做法 | 建议 |
|---|---|
| 纯 .bat + exe | 命令行为交互核心可保留（用户习惯、无运行时依赖），但**业务逻辑应抽到脚本/程序里** |
| 变量命名空间传值 | 保留这个思想，但用结构化配置替代 `set` 满天飞 |
| dev.csv 机型表 | **强烈建议保留并扩展**为首要设计——这正是数据驱动 |
| 17 套硬编码 Magisk 分支 | 改为**按 Magisk 版本探测/magiskboot 自适配**，消除硬编码 |
| 无引号路径 | 新工程必须全程加引号，支持空格路径 |
| 无一致性校验 | 加机型指纹校验（product/cpu/分区表布局），不匹配即阻断 |
| 单文件 1269 行主脚本 | 拆分为独立业务模块文件 |
