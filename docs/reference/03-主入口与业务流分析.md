# 03 · 主入口与业务流分析（煤油工具箱 / BFF）

> 分析对象：`煤油工具箱.bat`（1269 行）为主入口，`bin\framework.bat`（321 行）为 BFF 框架层，
> 以及 `input.bat`(61) / `sel.bat`(65) / `open.bat`(26) / `random.bat`(36) / `scrcpy.bat`(39) / `log.bat`(17)
> 交互基础件、`conf\dev.csv`(58) 机型库、`conf\fixed.bat`(2)、根目录引导脚本。
>
> **来源标注约定**：行号均以转码后的 UTF-8 文件为准，例如 `煤油工具箱.bat.txt:L1373`。
> 转码器（`_convert.py.txt`）为 `dst.write_text(txt, encoding='utf-8')`，在 Windows 上以 `\r\r\n` 落盘，
> 因此 **`read` / `grep` 工具看到的行号是权威行号**；PowerShell `Get-Content` 会把 `\r\r\n` 拆成两行，
> 行号约为权威值的 2 倍，**不可用**。本文所有行号取自 `read` / `grep`。
>
> 未能在代码中确证的内容一律写"未确认"，不做推测。

架构是典型的 **"主脚本 + 可复用框架 + 能力模块" 三层**：

```
煤油工具箱.bat  (业务编排层，只写流程，不写实现)
   │  call framework  <子命令>            ← 框架服务
   │  call write/read/chkdev/info/slot/... ← 能力模块
   │  goto <业务标签>                      ← 业务流自身
   ▼
bin\framework.bat (框架层：启动自检/日志/主题/CSV/磁盘/错误出口)
   │
   ▼
bin\*.bat (能力模块，每个都是 call <模块> <子命令> <args...> 的二级分发)
   │
   ▼
tool\Win\*.exe (本地可执行体)
```

**关键设计事实**：主脚本的**设备 I/O 全部经能力模块封装**，
唯一的例外是 `fastboot.exe`（`L785-L800` 共 16 条、`L873`、`L888`、`L911`、`L973`）和
`HexTool.exe`（`L828-L834`、`L866`）——这两类要求"精确控制单条命令/精确控制字节偏移"，
刻意不做封装。其余所有 adb/fastboot/fh_loader/QCNTool 调用都在模块内部。

## A. 启动链（boot sequence）

启动链严格分为 **8 个阶段**，每个阶段失败都会走统一 `FATAL` 出口。
下表按执行顺序给出：行号、动作、失败后果。

| # | 行号 | 动作 | 失败后果 |
|---|---|---|---|

| 2 | `L4` | `@ECHO OFF` | — |
| 3 | `L5` | `chcp 936>nul` 切换到 GBK 代码页 | 不检查返回值；若失败，后续所有中文提示将乱码，但流程继续 |
| 4 | `L6` | `cd /d %~dp0` 切到脚本所在目录（兼容从快捷方式/其他盘符启动） | 无检查 |

### A.3 日志系统与轮转（`bin__framework.bat.txt:L141-L158`）

```
L142  if not exist log.bat              → FATAL
L143  if "%framework_log%"=="n" set logfile=nul& set logger=CLOSED
L144  if "%framework_log%"=="n" SETLOCAL & goto STARTPRE-2      ← 关闭日志时跳到工具自检
L145  if not exist log md log          → FATAL
L146  for /f %%a in ('gettime.exe ^| find "."') do set logfile=%framework_workspace%\log\%%a.log
L147  set logger=UNKNOWN
L148  SETLOCAL
L149  set logger=framework.bat-startpre
L150  call log %logger% I 系统信息:%processor_architecture%.%winver%.工作目录:%framework_workspace%
L152  if "%framework_lognum%"=="" set framework_lognum=6       ← 默认保留 6 个日志
L153  for /f %%a in ('dir /B log ^| find /C ".log"') do (if %%a LEQ %framework_lognum% goto STARTPRE-2)
L154  for /f "tokens=1 delims=[]" %%a in ('dir /B log ^| find /N ".log"') do set /a var=%%a-%framework_lognum%
L155  :STARTPRE-1  L156 若 var 对应项已不存在 → STARTPRE-2
L157  删掉第 [var] 项日志；L158 set /a var+=-1 & 回到 L155
```

**轮转策略**：文件名是 `gettime` 时间戳，`dir /B` 天然按名字（≈时间）排序，因此 `dir` 的第 1 项是最旧的。
超出 `framework_lognum`（默认 6）后，从第 `总数-6` 项往前删——即**保留最新 6 个**，删更旧的。
这是"按序号倒删"的实现，逻辑正确但有个隐含前提：**日志文件名必须能按字典序=时间序排序**（依赖 `gettime` 的输出格式，未确认其字面格式）。

## B. BFF 框架设计（framework.bat）

### B.1 二级分发机制（`bin__framework.bat.txt:L15-L16`）

```bat
set args1=%1& set args2=%2& ... & set args9=%9
goto %args1%
```

**这是整个 BFF 的核心协议**：`call framework <子命令> <arg2> ... <arg9>` → 直接 `goto` 到**同名大写标签**。
所有能力模块（`write/read/chkdev/info/slot/reboot/partable/calc/clean/dl/imgkit/mzbox/open/sel/scrcpy/input/random`）
都逐字复制这 9 行模板（例如 `bin__read.bat.txt:L11-L12`、`bin__mzbox.bat.txt:L11-L12`）。

框架对外暴露的 8 个子命令（`bin__framework.bat.txt:L3-L11` 的文档头 + 实际标签）：

| 子命令 | 标签行 | 签名 | 返回值（导出变量） |
|---|---|---|---|
| `startpre` | `L110` | `startpre [skiptoolchk]` | 无（副作用：建立 4 个全局上下文变量） |
| `adbpre` | `L302` | `adbpre [文件名\|all]` | 无（副作用：adb push 到设备） |
| `theme` | `L97` | `theme [主题名]` | `c_i c_w c_e c_s c_h c_a c_we` |
| `conf` | `L82` | `conf <文件名> <变量名> <变量值>` | 无（副作用：写 `conf\<文件名>`，见 B.5） |
| `logviewer` | `L69` | `logviewer start <logfile>` / `logviewer end` | 无 |
| `loadcsvconf` | `L45` | `loadcsvconf <csv路径> [项] [orig\|full]` | `framework__loadcsvconf__<列名>`（或 orig 模式下的裸变量名） |
| `chkdiskspace` | `L21` | `chkdiskspace [盘符\|cur] <要比较的大小KB>` | `framework__chkdiskspace__enough` / `__spaceleft` |
| `FATAL` | `L320` | `FATAL` | 打印错误 + `pause` + `EXIT` |

**分发机制的硬约束**：`goto %args1%` 要求子命令名与标签名**完全一致**（大小写不敏感）。
用未定义的子命令 `call framework foo` 会导致 `goto` 到不存在的标签，cmd 直接报
`The system cannot find the batch label specified` 并以 exit code 1 终止**整个批处理进程**
（已实测确认），而不是只终止被 call 的文件。这是这个框架最脆弱的接口契约。

### B.2 ECHOC 彩色输出机制

`ECHOC` 是 `tool\Win\ECHOC.exe`，语法为 `ECHOC {颜色}{正文}{颜色}{\n}`。脚本从不硬编码颜色，
而是**全部引用主题变量**，形成 7 个语义色：

### B.4 CSV 配置加载器 `loadcsvconf`（`bin__framework.bat.txt:L45-L66`）

**设计**：把"逗号分隔表 + 首列是 `[key]`"的 CSV 转成一批 `set` 语句，再 `call` 那个临时 `.bat`，
从而把变量注入**调用者**的作用域（绕开 `SETLOCAL` 的作用域隔离）。

```bat
L51  if exist %tmpdir%\loadcsvconf.bat del ...        ← 清上次残留
L52  find "%item%" "%filepath%" || ECHOC ... goto FATAL   ← 先确认 key 存在
L53  set num=2
L54  :LOADCSVCONF-1
L55  if %num% GTR 31 → "配置项目过多...超出命令可容纳范围:31个" → FATAL
L57  for /f "tokens=%num% delims=[]," ... do set name=%%a      ← 从 #product 行取第 num 列名
L58  if "%name%"=="" goto LOADCSVCONF-2                       ← 列名取尽
L59  for /f "tokens=%num% delims=,"     ... do set value=%%a   ← 从数据行取第 num 个值
L60  if "%mode%"=="orig" → echo.set %name%=%value%              ← orig 模式：裸变量名
L61  否则               → echo.set framework__loadcsvconf__%name%=%value%
L62  set /a num+=1 & 循环
L64  ENDLOCAL
L65  call %tmpdir%\loadcsvconf.bat                            ← 注入调用者作用域
```

**这是一个很聪明的"反 SETLOCAL"技巧**，但代价明确：
- 上限 **31 列**（`L55` 硬编码），因为只有 `%1..%31` 可用；超出直接 FATAL
- `delims=[],` 意味着**列值本身不能含 `[` `]` `,`**
- `find "%item%"` 是**子串匹配**而非精确匹配：`loadcsvconf dev.csv [16S]` 会同时命中 `[16S]` 和 `[16Spro]` 行，
  靠 `L59` 循环覆盖取最后一次命中的结果（未确认是否稳定依赖行序）

**实际调用情况**：全工程 **零** 调用 `call framework loadcsvconf`（已 grep 确认）。
机型库实际走的是 `mzbox confdevpre`（见 D.2），`loadcsvconf` 是**框架提供但业务未使用的闲置能力**。

### B.5 配置文件写入器 `conf`（`bin__framework.bat.txt:L82-L94`）

```bat
L87  if not exist conf\%args2% echo.>conf\%args2%          ← 文件不存在则创建
L88  find "set %args3%=" "conf\%args2%" || echo.set %args3%=%args4%|findstr "set" 1>>conf\%args2% && goto CONF-DONE
L89  type conf\%args2% | find "set " | find /v "set %args3%=" 1>%tmpdir%\output.txt   ← 过滤掉旧值行
L90  echo.set %args3%=%args4%|findstr "set" 1>>%tmpdir%\output.txt                    ← 追加新值行
L91  move /Y %tmpdir%\output.txt conf\%args2% || ... goto FATAL
```

即 **"读全部 `set ` 行 → 剔除目标键旧行 → 追加新行 → 整体覆盖"** 的 upsert。
被用于：`framework conf user.bat product <product>`（`煤油工具箱.bat.txt:L1199`）、
`framework conf user.bat framework_theme <target>`（`L1264`）、
`framework conf dev-%product%.bat <列名> <值>`（`bin__mzbox.bat.txt:L317`）。

**副作用（重要）**：`L89` 的 `find "set "` 会把文件里**所有**含 `set ` 的行留下，
但也会**丢弃所有注释行、空行、非 set 行**。所以 `conf\user.bat` 一旦被 `conf` 写过，
就会从"手写配置文件"退化成"纯 set 列表"。这是可接受的，但意味着**不要在 `user.bat` 里写注释**。

### B.8 统一错误出口 `FATAL`（`bin__framework.bat.txt:L320-L321`）

```bat
:FATAL
ECHO. & if exist tool\Win\ECHOC.exe (tool\Win\ECHOC {%c_e%}抱歉, 脚本遇到问题, 无法继续运行. 请查看日志. {%c_h%}按任意键退出...{%c_i%}{\n}& pause>nul & EXIT)
     else (ECHO.抱歉, 脚本遇到问题, 无法继续运行. 按任意键退出...& pause>nul & EXIT)
```

设计要点：
- **双重兜底**：`ECHOC` 不存在时退化为纯 `ECHO`（因为 `FATAL` 可能在 `ECHOC` 自检失败时被调用，`L132`）
- **每个模块文件末尾都复制了一份相同的 `:FATAL`**（`input.bat:L58-L59`、`sel.bat:L64-L65`、
  `open.bat:L25-L26`、`random.bat:L34-L35`、`scrcpy.bat:L38-L39`、`log.bat:L16-L17`、
  `read.bat:L208`、`write.bat:L573`、`calc.bat:L211`、`chkdev.bat:L194`、`mzbox.bat:L326`、
  `煤油工具箱.bat.txt:L1268-L1269`）
- **`EXIT` 而非 `EXIT /B`**：终止整个 `cmd` 进程，不返回调用者。这是**刻意设计**——
  遇到不可恢复错误时不允许业务脚本"捕获后继续"

**主脚本的 `goto FATAL` 密度**：`煤油工具箱.bat.txt` 中共 **32 处** `goto FATAL`。

### B.9 "框架能力" vs "业务脚本必须遵守的约定"

这一区分是本次分析的核心结论之一：

**A. 框架提供的能力（业务方按需调用即可）**

| 能力 | 入口 | 说明 |
|---|---|---|
| 启动自检 | `framework startpre` | 环境 + 29 项工具 |
| 主题配色 | `framework theme <名>` | 输出 7 个颜色变量 |
| 配置持久化 | `framework conf` | upsert 到 `conf\*.bat` |
| CSV 加载 | `framework loadcsvconf` | 注入 `framework__loadcsvconf__*` |
| 磁盘检查 | `framework chkdiskspace` | 输出 `framework__chkdiskspace__*` |
| 设备侧工具推送 | `framework adbpre` | push + chmod |
| 实时日志窗 | `framework logviewer start/end` | 独立窗口 tail -f |
| 统一错误出口 | `goto FATAL` | 红字 + pause + EXIT |
| 日志写入 | `call log <logger> <级别> <文本>` | 级别 `I/W/E/F` |
| 文件/文件夹选择器 | `call sel file\|folder [s\|m] <起始目录> [过滤器]` | 输出 `sel__*` |
| 菜单输入 | `call input choice [……]#[默认]` | 输出 `choice` 与 `input__choice` |
| 打开外链/文件 | `call open common\|folder\|txt\|pic` | — |
| 随机串 | `call random <长度> [字符池]` | 输出 `random__str` |
| adb 投屏 | `call scrcpy <标题> [wait]` | — |

**B. 业务脚本必须遵守的约定（违反会静默出错）**

1. **变量命名空间**：能力模块的输出必须用 `<模块>__<子命令>__<字段>` 双下划线三段式，
   业务侧只读不写。实例：`chkdev__port__qcedl`(`chkdev.bat:L184`)、
   `mzbox__adbreadinfo__chipid`(`mzbox.bat:L80`)、`info__fastboot__unlocked`(`info.bat:L153`)、
   `slot__cur`(`slot.bat:L56`)、`sel__file_path`(`sel.bat:L36`)、`calc__numcomp__result`(`calc.bat:L41`)。
2. **必须用 `ENDLOCAL & set X=Y` 导出**：能力模块内部一律 `SETLOCAL`（如 `chkdev.bat:L19`、
   `read.bat:L72`、`write.bat:L423`），因此**只能**在 `ENDLOCAL &` 之后的行上把值写回调用者作用域。
   业务侧必须等 `call` 返回后再读。
3. **禁止直接 `goto` 进能力模块**：必须 `call`，否则 `EXIT`/`:FATAL` 会带走整个进程。
4. **UI 宽度契约**：分隔线固定
   `=--------------------------------------------------------------------=`（70 字符），配合 `mode con cols=71`（`L25`）。
   所有业务页面的 `ECHO.=` 行必须严格这个长度，否则边框错位。
5. **每条 `ECHOC` 必须以 `{%c_i%}{\n}` 收尾**，否则颜色会"漏"到后续输出。
6. **业务脚本不自己建 `tmp`/`log`**，一律用 `%tmpdir%` / `%logfile%`。
7. **重定向约定**：长命令输出写 `1>>%logfile% 2>&1 || goto FATAL`；
   需要判断结果的先写 `%tmpdir%\output.txt` 再 `type ... >>%logfile%` 再 `find`。
8. **`tmpdir` 单例假设**：默认 `framework_multitmpdir=n`（`L138`），所有模块共用同一个 `%tmpdir%`，
   因此**业务脚本不能在多个标签间并发使用 `%tmpdir%\output.txt`**（本项目是单线程菜单，天然安全）。

因为该机型"不支持9008"（机型名即注明，`dev.csv:L19`）。

三路都汇合到 `SAVEDATA-PRIVATE-READID-1`（`L324`）：

| 项 | 标签 | 流程 |
|---|---|---|
| `2` 获取解锁和授权码 | `SAVEDATA-PRIVATE-GETDATA`(`L338`) | 打开金山文档(`L339`) |

**MZKV vs PRIVATE 的核心差异**：

| 维度 | MZKV | PRIVATE |
|---|---|---|
| 解锁凭据载体 | **镜像文件** `mzkv_unlock.img`（刷分区） | **文本解锁码** 512 位 hex（写进 private.img 偏移） |
| 需读取的 ID | 仅 `SocID`（`L217`） | `ChipID` + `SocID`（`L330`） |
| ID 读取通路 | 仅 adb（`L210`） | **adb / fastboot / edl 三通路** |
| 授权码 | `sig` 变体需要，`nosig` 不需要 | 需要 |
| 需回读原分区备份 | 是（mzkv，7z 打包，`L258-L266`） | 否 |

### C.2 `1` 解锁 BL（`UNLOCKBL`，`L687-L928`）

**风险告知页（`L697-L716`）**：列出 4 类后果（TEE假死 / 解锁后必须格式化 / 部分设备不能 OTA / 再上锁非常危险）
和 8 项准备（含 `edlplan==edlcable` 时要求"9008数据线"，`L706`）。`pause>nul` 确认（`L716`）。

**六方案分流（`L718`）**：`goto UNLOCKBL-%blplan%`。
标签 `UNLOCKBL-AUTH-MZKV-SIG`(`L720`)、`-AUTH-MZKV-NOSIG`(`L721`)、`-AUTH-MZKV`(`L722`)、

`L719` 紧跟一个 `goto FATAL`，是**未知 `blplan` 的兜底**。

**Fastboot 通路（`UNLOCKBL-AUTH-PRIVATE-FB`，`L778-L817`）**：

这是全工程最"仪式感"的一段代码 —— **512 位解锁码被切成 16 段，每段 32 字符，
通过 16 条独立的 `fastboot oem unlock:<hex>` 命令依次下发**：

```bat

L786  fastboot oem unlock:%blunlockcode:~32,32%
L787  fastboot oem unlock:%blunlockcode:~64,32%
L788  ... ~96  (ECHOC 文案: 梦想 /)
L789  ... ~128 (追求)
L790  ... ~160 (源)
L791  ... ~192 (于)
L792  ... ~224 (热爱 /)
L793  ... ~256 (创造)
L794  ... ~288 (无)
L795  ... ~320 (界)
L796  ... ~352 (可能 /)
L797  ... ~384 (为你)
L798  ... ~416 (开)
L799  ... ~448 (启)
L800  ... ~480 (未来)
L801  reboot fastboot fastboot chk
L802  info fastboot → L803 校验 unlocked 必须为 yes
L805-L809  forcefb=y：write fastboot misc misc_wipedata.img + reboot → DONE

**每段 32 字符 × 16 = 512**，与 `L763-L765` 校验的 512 位严格对应。
`ECHOC {%c_we%}` 后跟的那串字（极致/源/于/梦想…）是把每行命令的提示文字拼成一句 slogan，
**同时兼作"进度指示"**——用户从文案推进能看出进行到第几步。这是很巧妙的 UI 手法。

**EDL 通路（`UNLOCKBL-AUTH-PRIVATE-EDL-1`，`L819-L856`）—— HexTool 改 private.img 偏移**

```

L826  copy bak\private_<ts>.img → %tmpdir%\private.img
L828  HexTool.exe %tmpdir%\private.img 00069632 4   4C4F434B
                  ↑偏移(十进制69632=0x11000) ↑长度4 ↑"LOCK"(ASCII hex)
L829  HexTool.exe %tmpdir%\private.img 00069636 256 %blunlockcode%
                  ↑偏移0x11004        ↑256字节 = 512 hex字符
L830  HexTool.exe %tmpdir%\private.img 00069892 16  666163746F7279000000000000000000
                  ↑偏移0x11104  ↑"factory" + 8×00
L831-L834  set str=6D54657374332E31302E372E30000000   ("mTest3.10.7.0")
           meizu18s    → 726465352E342E352E30000000000000  ("rde5.4.5.0")
           meizu18sPro → 同上

                  ↑偏移0x11114

L845  reboot qcedl qcedl <port>
L846  chkdev qcedl rechk 1

**偏移量解读**（十进制 → 十六进制，均已在代码注释中标明）：
- `69632` = `0x11000`（注释 `L556` 处的 `::0x11000` 对应读取位置，写入口的 `L828` 同址）
- `69636` = `0x11004`（`0x11000 + 4`，紧跟 "LOCK" 魔数之后）
- `69892` = `0x11104`（`0x11000 + 0x104`）

即 **private 分区 0x11000 处是一个结构体**：
`[4B "LOCK"][256B 解锁码][…][16B "factory"+pad][16B 版本串]`。
`L836-L838` 的注释保留了备选魔数：`mTest3.10.7.0` / `rde5.4.5.0` / `meizubl.com`。
`L840-L843` 则保留了 **第二个解锁码槽位（0x14000 系）的完整命令但整体注释掉**——
说明 0x14000 槽位曾被使用、后被禁用（未确认禁用原因）。

#### persist 分区保护逻辑（`L405-L406`）

```bat
::不刷入persist分区以免损坏tee
busybox.exe sed -i "s/ filename=\"persist.img\" / filename=\"\" /g" ^
    %sel__folder_path%\%product%_MEIZUBOX_ParBak_%baktime%\images\rawprogram0.xml
```

**机制**：`edlreadall` 生成的 `rawprogram0.xml` 里会有
`filename="persist.img"` 的 `<program>` 条目。这条 `sed` 把它替换成 `filename=""`，
于是**备份包仍是完整的（persist.img 文件还在 `images\` 里），但用这个包去刷机时会跳过 persist**。
注释写明理由：**"不刷入persist分区以免损坏tee"**。

**为什么危险**：`persist` 分区存放 TEE（Trusted Execution Environment）相关数据，
包含指纹、密钥、DRM 证书等。**用别的机器的 persist 覆盖本机 persist 会导致指纹永久失效、
TEE 功能异常**。这一保护确保"备份包可以安全地刷回同一台或另一台设备而不破坏 TEE"。

**注意该 sed 只作用于 `rawprogram0.xml`**（LUN 0）。如果 persist 位于其他 LUN，
这条保护会失效——但按高通通用布局 persist 通常在 LUN 0（未在代码中确证，
`mzbox.bat:L224` 的 sed 也只针对固定几个分区名）。`L224` 的排除清单是：
`userdata`、`last_parti`、`mindowsesp`、`mindowswin`、`mindowsdat`。

**`L390` 与 `L389` 说明的差异**：`L389` 说"备份除 userdata 和 last_parti 外的所有分区"，
由 `mzbox.bat:L224` 的 sed 实现（把 `[userdata]` 等方括号去掉 → 表示不回读）；
`L404` 复制 xml 是为了让 `images\` 目录**自身就是一个可用 9008 包**（注释 `L390`："备份包即9008包"）。

**`L398` 的时间戳细节**：全工程几乎所有时间戳都用 `for /f %%a in ('gettime.exe')`，
但 `L398`、`L490`、`L497`、`L504`、`L860`、`L900`、`L901`、`L902`、`L1139` 用了
`('gettime.exe ^| find "."')` 变体。**含义差异未确认**（推测为处理换行/格式差异）。

这是有意为之：兼容"历史上用旧版本工具写入过第二槽位"的设备。

**`L563`/`L577` 的 `if %var% EQU 0` 是什么**：`EQU` 是**数值**比较，
`%var%` 是 256 个 hex 字符（如 `A1B2...`）。若首字符是字母，cmd 会把整个串当字符串比较，
`EQU 0` 不成立 → 继续。若整个串是全 `0`（未写入的空白槽位），cmd 会把它解析为数字 0 → 判为"位置为空"。
**这是个巧妙的"判断槽位是否全零"技巧**，但依赖 cmd 的八/十六进制解析怪癖，脆弱。

**`L565-L566` 与 `L579-L580` 都覆盖 `blunlockcode.txt`**：所以若两个槽位都读成功，
**`blunlockcode.txt` 最终会是位置2的值**（后者覆盖）。这可能是缺陷（位置1通常才是有效的），
也可能是刻意（新机型用位置2）。**未确认**。

- `cmd`：设备可从 Fastboot/系统**用命令**重启进 9008（`L811` `reboot fastboot qcedl`、`L1134` `reboot system qcedl`）
- `key`：只能**手动按键**（长按电源+音量加减）进 9008（`L812`、`L1134` 的 else 分支）

### D.2 机型配置的生成与加载（`mzbox confdevpre`，`bin__mzbox.bat.txt:L308-L323`）

**这是 CSV → 配置文件的转换器**：

```bat
L311  set num=2
L313  if %num% GTR 31 → "配置项目过多...请QQ联系1330250642" → FATAL
L314  for /f "tokens=%num% delims=[]," %%i in ('find "[product]" "conf\dev.csv"') do set name=%%i
      ↑ 从字段名行(L2)取第 num 列的名字
L315  if "%name%"=="done" goto CONFDEVPRE-2                        ← 遇到 done 列则停止
L316  for /f "tokens=%num% delims=," %%i in ('find "[%product%]" "conf\dev.csv"') do set value=%%i
      ↑ 从机型行取第 num 列的值
L317  call framework conf dev-%product%.bat %name% %value%         ← 逐列写入配置文件
L318  set /a num+=1
L319  goto CONFDEVPRE-1
L322  call conf\dev-%product%.bat                                  ← 最后加载一次
```

**我用等价脚本实测验证过**（产品=`meizu20`），生成结果为：
```
[2] name=model        value=魅族20，20C
[3] name=cpu          value=骁龙8Gen2
[4] name=storagetype  value=ufs
[5] name=blplan       value=auth-private
[6] name=parlayout    value=ab_rec
[7] name=bootpar      value=init_boot
[8] name=edlplan      value=edlcable
（num=9 时 name=done → 停止）
```
即 `product` 自己不进配置文件（它由 `conf\user.bat` 保存）。

**调用点（`煤油工具箱.bat.txt:L1196-L1201`，`:SELDEV-1`）**：
```
L1198  call mzbox confdevpre                  ← 重建 conf\dev-<product>.bat
L1199  call framework conf user.bat product %product%   ← 记住选择
L1200  call conf\dev-%product%.bat            ← 载入
L1201  goto MENU
```

**为什么不用 `framework loadcsvconf`**：`confdevpre` 直接调 `framework conf`（upsert），
比"生成临时 set 脚本再 call"多一次文件 I/O，但好处是 **配置持久化到磁盘**——
下次启动 `L16` 能直接 `call conf\dev-%product%.bat`，不必再从 CSV 解析。这是性能优化。

### D.3 `blplan` 枚举（7 种）及其驱动分支

| `blplan` | 含义 | 解锁入口 | `0` 号功能 | 关键行号 |
|---|---|---|---|---|
| `auth-private` | 需解锁码（512位文本）+ 授权码；写 `private.img` 偏移 | `-AUTH-PRIVATE`(`L753`) | 显示"导入解锁授权码" | `L184`、`L753` |
| `auth-mzkv-sig` | 需解锁 mzkv 镜像 **+** 授权码（9008 需 sig） | `-AUTH-MZKV`(`L722`) | 显示"导入解锁mzkv和授权码" | `L185`、`L720` |
| `auth-mzkv-nosig` | 只需解锁 mzkv 镜像（9008 免授权） | `-AUTH-MZKV`(`L722`) | 同上，但 2/3 步隐藏 | `L186`、`L721` |
| `odm-1` | ODM 免解锁码，改 frp 末字节 + `flashing unlock` | `-ODM-1`(`L857`) | 提示"不限制解锁和9008, 无需解锁码" | `L57`、`L857` |
| `odm-2` | ODM，用 SN 作解锁码 | `-ODM-2`(`L880`) | 同上 | `L57`、`L880` |
| `odm-note8` | ODM Note8 专用，换 aboot 解锁 | `-ODM-NOTE8`(`L897`) | 同上 | `L57`、`L897` |
| `avb` | **仅在枚举参考区出现**（`L38`），无对应标签，无机型使用 | → `goto FATAL`(`L719`) | 无 | `L38` |

**`avb` 的悬空引用是个隐患**：若有人把机型标成 `avb`，`L718` 会 `goto UNLOCKBL-avb`，
标签不存在 → cmd 报错并**终止整个进程**（已实测该行为）。`L719` 的 `goto FATAL` 位于
`L718` 之后，**在 `goto` 已失败的情况下永远不会执行**（`goto` 失败是致命的，不是可继续的）。
这是"看似有兜底，实际兜底无效"的典型写法。

### D.4 `parlayout` 枚举（3 种）及其驱动分支

| `parlayout` | 含义 | Recovery 刷入策略 | 槽位功能 | Root 目标分区 |
|---|---|---|---|---|
| `aonly` | 非 A/B，单一分区集 | 刷独立 `recovery`(`L488-L494`) | **不可用**（`L421`） | `%bootpar%` |
| `ab` | A/B，**无**独立 recovery | 注入 TWRP 到 `boot_<slot>`(`L502-L509`) | 可用 | `%bootpar%_<slot>`(`L1118`) |
| `ab_rec` | A/B，**有**独立 recovery | 刷 `recovery_<slot>`(`L495-L501`) | 可用 | `%bootpar%_<slot>` |

`ab`/`ab_rec` 的判定统一用 `if "%parlayout:~0,2%"=="ab"` 前缀匹配（`L1071`、`L1117`），
而非精确等于——这样 `ab_rec` 也能被识别为"是 A/B 设备"。**这是正确的写法**。
但 `L453` 用的是 `if not "%parlayout%"=="ab"`（精确匹配），因此 `ab_rec` 机型也会看到
"官方boot开机时可能自动将recovery恢复官方"的提示——对 `ab_rec` 机型其实是**多余的警告**（小瑕疵）。

## E. 关键风险点

### E.1 会变砖 / 丢数据的操作（按严重度降序）

| 级别 | 操作 | 位置 | 后果 | 现有保护 |
|---|---|---|---|---|
| **P0 报废** | `meizu20inf` 切换槽位 | `slot.bat:L16-L21` | 机型名直接标注"不支持9008"，切槽位后**无法救回**（官方明示报废） | ① 主菜单常驻警告(`L53`) ② `slot.bat` 二次确认 ③ 选 1 则 `goto FATAL` |
| **P0 报废** | `meizu20inf` 进 fastbootd | `reboot.bat:L20-L25` | 同上，`fastboot reboot fastboot` / `adb reboot fastboot` 会导致报废 | ① 主菜单警告(`L53`) ② `reboot.bat` 拦截并二次确认 |
| **P1 变砖** | 上锁 BL（`111`） | `LOCKBL:L930-L977` | 所有非官方固件无法启动；若系统未完全恢复官方 → **无法开机**；且上锁后无法再刷写 | ① 大段后果说明(`L940-L954`) ② 二次确认页(`L964-L967`) ③ **默认值=暂不上锁**(`L968` 的 `#[1]`) ④ 先刷 `misc_wipedata`(`L972`) |
| **P1 变砖** | 解锁 BL 中断 | `UNLOCKBL` 全流程 | 解锁过程中设备处于半解锁态；格式化未完成可能导致无法开机 | ① 6 处"仍要继续"确认(`L745-L746`、`L783`、`L803`、`L849-L850` 等) ② 完成页提示手动 Recovery 清数据(`L927`) |
| **P1 变砖** | `odm-note8` 未恢复 aboot | `L904-L905` vs `L920-L921` | 设备停在"解锁版 aboot"上，非正常状态 | ① 明确提示"设备现在处于非正常状态"(`L918`) ② 自动恢复流程(`L917-L925`) ③ 备份原始 aboot/abootbak(`L901-L902`) |

### E.4 关于 `goto` 失败模式的重要结论

经实测确认：**`goto <不存在的标签>` 不会返回错误码给调用者，而是直接终止整个 cmd 进程**
（输出 `The system cannot find the batch label specified - XXX`，exit code 1）。

这对 BFF 框架有两层含义：

1. **`goto %args1%` 分发是"全有或全无"的**：任何 `call framework <未知子命令>` 都会
   杀死整个工具，而不是让业务脚本捕获错误。这解释了为什么 `framework.bat:L15-L16`
   没有任何参数校验代码——校验失败本身无法挽回。
2. **"兜底 `goto FATAL`"模式（`L719`、`L187` 等）只在"前一条 if 未匹配"时有效**，
   对"`goto` 目标不存在"完全无效。写兜底时必须用 `if not exist` 检查标签或改用 `if/else` 结构。

#### F.1.1 `命令行.bat` 设计要点

这是一个**绕过框架、独立自举**的调试入口（`L8-L22`），值得单独一提：

```bat
L8   cd /d %~dp0
L9   if exist bin (cd bin) else (echo 找不到bin & goto FATAL)
L10  if not exist tmp ECHO.找不到tmp & goto FATAL      ← 硬依赖 tmp 已存在（不自动建）
L11  set path=%cd%;%cd%\tool\Win;%path%
L12  set framework_workspace=%cd%                      ← 手工复刻框架变量
L15-L22  手工复刻 ECHOC / strtofile 自检
```

**它故意不调用 `framework startpre`**（因为 startpre 只允许从主入口跑，
且 `命令行.bat` 在 `tmp` 缺失时就直接退出、不建目录）。因此它**没有 `%tmpdir%` / `%logfile%` 变量**，
